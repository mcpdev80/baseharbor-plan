# v0.4.31 · Final semantic acceptance

Source: [baseharbor#174](https://github.com/mcpdev80/baseharbor/issues/174). Tasks: [views/releases/v0.4.31.md](../views/releases/v0.4.31.md). Parent roadmap: #155 · agent interface #215 · lifecycle semantics #172.

This note keeps **every acceptance item of the source**. Long historical planning sections (v0.4.25 session plans, the 2026-10-10 two-session split and the shared release-PR rule) are summarized; the original text is in the [snapshot](../migration/source-snapshot/baseharbor/174.json).

## Current boundary

Pure final semantic and security acceptance of the previously delivered base. TLS/proxy changes (core-902) and attack protection (core-903) are implemented and qualified in v0.4.30 and only checked here. **No new major feature or provider development** in this acceptance; real defects found must be fixed before approval. Depends on qualified prior releases including v0.4.30. Afterwards the no-new-features stability reconciliation and the v0.5 freeze (#175). From v0.4.26, core-888 applies (small task PRs, verified evidence reuse); the older session/shared-branch sections are historical planning, not the current working mode.

## Goal

Close v0.4 by proving that BaseHarbor's language and lifecycle semantics are runtime-independent while Compose remains the complete reference runtime. No new major capability and no Kubernetes implementation. Developer experience first; simple by default, secure by default, explicit when needed; as little as possible, as much as necessary.

## Boundaries to prove

- **State classes:** portable application state (stable identity, logical capability requirements, logical resources, endpoint/exposure intent, secure-binding requirements, application-owned health/security requirements); deployment/operator state (environment, runtime and capability-provider selection, placement, sharing boundaries, policy overrides); runtime-owned realization state (Compose project names, generated overrides, host ports, Docker/Podman network/container details, local paths; future Kubernetes namespaces/resources/Services/PVCs); provider-owned state (physical bucket/database identities, provider credentials, topology/product config, provider lifecycle metadata); generated/protected state (generated credentials, fingerprints, runtime identity) outside portable intent.
- **Runtime-provider rule:** capability providers and runtime providers are separate axes. v0.4 proves the boundary and the Compose implementation; a future Kubernetes runtime consumes the same semantics without redefining intent. No speculative runtime-provider framework.
- **Reference journeys:** human — inspect → app init/adopt → plan → up/apply → status → doctor → update → backup → restore → drift/repair → destroy. Agent/machine — discover → inspect → plan → policy → safe mutation → status/doctor → verification/evidence.
- **Semantic acceptance:** CLI, JSON and MCP use the same state/result semantics; runtime-specific names never become application identity; provider placement can change without rewriting intent; Compose realization stays behind a runtime boundary; status/doctor/policy/evidence agree on actual state; readiness is reported through real verification; lifecycle operations preserve ownership and isolation; no later-runtime concepts leaked into the v0.4 portable contract.
- **Developer experience:** five-minute local journey stays valid; configuration stays sparse; resolved state is explained without provider noise; dangerous ambiguity fails closed with guidance; no security questionnaire; no new knob without a demonstrated use case; consistent terminology; current behavior documented and future Kubernetes behavior marked future.
- **Capability semantic sufficiency** (SQL, cache/key-value, S3 as representative families): can an application express a required protocol/feature semantic without naming a product; can a provider declare its supported subset; can planning/conformance reject an incompatible provider before mutation; is feature compatibility kept separate from availability/topology; does normal intent stay sparse for default semantics. **A failure blocks the v0.5 freeze.**
- **Delivery boundary:** Runtime, Capability and Delivery Provider are distinct; direct delivery is not a universal assumption; delegated delivery needs no intent change; reconciliation ownership is explicit and singular; delivery selection is deployment/operator state; Compose stays the first-class direct path; future GitOps providers need no product fields in intent.
- **Standards-first runtime boundary** (#396, closed): Docker and Podman use the same provider-neutral runtime boundary intended for third-party runtimes; no direct `bhruntime.Compose` coupling in portable orchestration; product-specific branching stays in providers; BaseHarbor-specific semantics need a documented standards gap (#390/#396); a conforming future runtime needs no intent change; Compose is first-class but not the identity of the runtime abstraction.
- **MCP / machine-interface parity gate:** new or changed semantics go through the shared domain core and update CLI + JSON + MCP together; MCP reuses the shared core and never wraps CLI subprocesses; no shell/Docker/Compose/Podman/provider escape hatch; read-only/mutating/destructive classes explicit; policy, ownership, preflight, reconciliation, verification, confirmation and secret-safety identical across human and agent paths; unsupported agent operations fail with typed results; docs, discovery and generic MCP-client acceptance updated in the same release; the MCP surface stays small and semantic. This is a release gate.
- **Stable identity:** #483 (closed) — freeze durable technical identity, not mutable names.
- **No dead-end errors** (#375, closed): "If BaseHarbor says no, it also says why and how to continue."
- **Pre-freeze compatibility rule:** before the v0.5 freeze there is no legacy compatibility, migration or alias requirement and no preservation of obsolete pre-freeze behavior. Replace wrong designs with the correct model; add no legacy modes, migration layers for pre-freeze state, deprecated paths, historical aliases, duplicate documentation trees or shims. Guarantees begin when a contract is intentionally frozen/versioned in v0.5.x.
- **Umbrella rule:** this issue owns scope, ordering, cross-cutting acceptance and completion; implementation lives in focused child tasks that reference this release; do not mirror headings into tickets.
- **Independent developer validation:** at least one developer who did not implement the path completes the public reference journey from shipped documentation without undocumented help, from a clean or realistically independent setup. Capture time to first successful run, unclear/unnecessary prompts, undocumented prerequisites/workarounds, dead-end errors, terminology/navigation confusion, auth/onboarding friction and any point needing implementation knowledge. If a normal developer cannot complete the documented happy path without private implementation knowledge, v0.4 acceptance is not complete.
- **Kubernetes architecture proof (draft PR #616):** must be explicitly resolved before this release closes. It is not a Kubernetes support release; its question is whether Kubernetes can consume the final semantics without new Application, Capability, Identity, Policy or user-facing Core contracts. Re-evaluate against the final contract/head (not its September baseline); validate the same intent without Kubernetes fields, Target/namespace separation, stable identity, runtime-neutral bindings, ownership-safe destroy, namespace-scoped operation, and no Kubernetes-specific Core fork for READY/status/doctor/evidence and CLI/JSON/MCP; fix genuine missing portable primitives; decide: accept, supersede with current-head evidence, or reject with rationale. "Open/forgotten draft ≠ portability evidence." No production Kubernetes hardening, storage/HA/Gateway parity, Operator/CRDs or OpenShift support is required unless a missing contract would otherwise be frozen incorrectly.
- **Console AI assistant boundary:** Console AI assistant → MCP/Machine contract → Core → policy/authorization/approval → Target Access. Non-goals: no built-in assistant implementation, no AI provider integration, no model hosting, no AI-specific Core service, no AI bypass of MCP/machine authorization. Passing means an assistant can be added after v0.5 without reopening the frozen model. (v0.4.28 owns the explicit product decision.)

## Acceptance

### Core acceptance
- Normal application intent remains sparse when no non-default feature requirement exists.
- Incompatible providers are rejected before mutation.
- Representative capability specs prove semantic compatibility beyond capability-name matching.
- A representative Compose application completes the full lifecycle end to end.
- CLI/JSON/MCP expose the same semantic truth.
- A generic MCP client can discover and exercise the supported semantic surface.
- Capability-provider implementation/placement changes do not rewrite portable application intent.
- Every important state field can be classified as portable, deployment/operator, runtime, provider or protected/generated state.
- Compose project/port/network/override details are confirmed as runtime-only realization.
- No Kubernetes/OpenShift resource primitive exists in portable application intent.
- Status/doctor/policy/evidence agree.
- Backup/restore and repair/destroy remain ownership-safe.
- Exact-head acceptance evidence is captured economically.
- Optional ecosystem work remains deferred.
- No domain/lifecycle behavior exists only in CLI rendering.
- Release blockers for the v0.5 freeze are explicit.

### Pre-freeze architecture checklist
Any failed item that requires a new portable primitive blocks the v0.5 freeze; product-specific convenience, admin UIs and optional integrations do not.

*Identity:*
- Application identity and BaseHarbor operator identity remain separate.
- Managed application identity from #363 fits the existing capability/provider/lifecycle model.
- Identity-provider realization does not leak Keycloak-specific concepts into portable application intent.
- Workload/machine identity, human identity and provider-admin credentials remain distinct.

*Secrets and credentials:*
- Human end-user credentials remain owned by the identity provider and are not mirrored into OpenBao.
- Machine/provider secrets use secure bindings and protected/generated state.
- Long-lived unrestricted provider-admin credentials are not exposed to applications.
- Rotation/revocation can occur without rewriting portable application intent.

*Network and connectivity:*
- Portable semantics can express required connectivity direction and exposure intent without runtime-specific networking fields.
- Public/private/internal exposure remains deployment/provider realization rather than product-specific application configuration.
- Deny-by-default relationships and explicit required connectivity remain enforceable.
- Future Kubernetes NetworkPolicy, service-mesh, VPC/subnet and firewall realization can fit without changing portable intent.

*PKI and certificate lifecycle:*
- Certificates, private keys and trust material are protected/generated state or external references, never ordinary portable application data.
- Ownership of CA/trust anchors and issued certificates is explicit.
- Expiry/invalid trust is observable and actionable.
- Rotation/reissuance can reconcile safely.
- mTLS requirements can be expressed provider/runtime-neutrally without embedding a specific PKI product.

*Backup and restore:*
- Backup success requires verification, not only artifact creation.
- Restore includes compatibility preflight, data/state restoration, rebind/reconcile and semantic verification.
- Provider-owned data backup remains the responsibility of the provider that understands its data semantics.
- Ownership and foreign/platform-managed resources remain safe during restore/recovery.
- Backup/restore metadata is sufficient for later version/runtime compatibility handling.

*Artifact and supply chain:*
- Runtime/provider artifacts have deterministic identities where practical, including digest/version identity.
- Artifact provenance/signature/SBOM evidence can be attached or verified later without changing portable application intent.
- Production policy can reject ambiguous or unverifiable artifacts without product-specific fields in the app contract.
- Registry/distribution location remains a deployment/operator/runtime concern, consistent with #181.
- No pre-v0.5 requirement is created to implement a specific signing, SBOM or registry product.

*Audit, evidence and ownership:*
- Security-sensitive lifecycle decisions produce secret-safe evidence.
- Ownership is explicit across application, shared, external/platform and protected/generated state.
- Audit/evidence can identify the effective policy, actor/workload identity, provider/runtime and verified outcome without storing secret material.
- Drift/repair/destroy remain ownership-safe across every reviewed boundary.

*Interface parity:*
- CLI, JSON and MCP expose the same semantic truth for the reviewed boundaries.
- No required lifecycle/security behavior exists only in CLI presentation code.
- Unsupported/unverifiable/denied/conflict/foreign-owned/degraded results remain typed and machine-readable.

### Target boundary (#408 Target model is not redesigned)
- Runtime, Capability and Delivery Provider work does not introduce a second Target/Context model.
- Runtime Provider selection is consumed from the resolved Target rather than portable application intent.
- Access Reference and Scope remain deployment/operator state established by #408.
- Multiple Targets and multiple deployments remain isolated through the #408 Target-scoped state model.
- CLI, JSON and MCP continue to expose the same effective Target/deployment identity.
- Portable application intent remains unchanged when the Target changes.
- Runtime/provider refactors preserve #408 ownership and fail-closed Target semantics.

### Workload source / repository adoption (#519)
- Compose, Quadlet, Kubernetes manifests, Kustomize and Helm are classified as repository workload sources/adoption inputs, not portable runtime identities.
- The portable Application Contract does not require source kind/path.
- Existing workload.compose compatibility is preserved without freezing Compose as canonical workload identity.
- Logical workload component identity remains stable across source-native representations.
- Repository source metadata is separated from portable application intent, Target state and runtime/provider state.
- app inspect/init use the same normalized evidence semantics across supported source adapters.
- Understanding a Kubernetes/Helm/Kustomize repository does not imply runtime support or ownership of live Kubernetes resources.
- Runtime Provider and Delivery Provider compatibility is checked after source inspection/adoption through typed plan/preflight results.
- CLI/JSON/MCP expose the same source-neutral repository semantics.

### Actionable diagnostics (#375)
A v0.5 freeze is not complete if failure semantics still exist only as arbitrary error strings.
- Known failures use one shared typed diagnostic/problem model below presentation layers.
- CLI, JSON and MCP expose the same cause/remediation semantics.
- Fail-closed outcomes explain both the reason and the safe path forward.
- Unsupported, invalid, denied, unverifiable and foreign-owned results remain distinguishable.
- Known recoverable failures offer/propose safe repair where BaseHarbor can do so deterministically.
- Every known unrecoverable failure provides the next useful action.
- Raw provider/runtime errors are diagnostic detail, not the primary human message.
- Plan, Preflight, Doctor and lifecycle commands do not maintain competing error taxonomies.
- Tests protect semantic problem fields and secret-safe rendering.

- The reference demo config matrix (#553) proves valid capability subsets, mixed combinations and invalid cross-capability contracts; the full-feature demo alone is not sufficient.
- Semantic acceptance uses the final human CLI surface (#603) and proves CLI simplification created no second lifecycle or divergence from JSON/MCP.

### Console AI assistant
- An AI assistant is classified as a client of the existing Machine/MCP surface, not a new authority.
- It cannot call Docker, Podman, Kubernetes, OpenShift or the Node Connector directly.
- Read-only discovery/planning can reuse existing machine safety metadata.
- Mutating/destructive operations remain subject to the same authorization, policy, confirmation and approval semantics as every other client.
- AI/provider endpoint configuration is Console/platform configuration, not portable Application Intent.
- Model/provider choice remains replaceable and does not enter BaseHarbor domain contracts.
- AI credentials use the existing protected secret/credential boundary and are not persisted as ordinary browser-local state.
- No new BaseHarbor lifecycle or tool semantics are introduced only for AI.
