# v0.4.29 · Linux, WSL2 and macOS

Source: [baseharbor#876](https://github.com/mcpdev80/baseharbor/issues/876). Implementation epic: [core-818](../epics/core-818-host-platforms.md). Tasks: [views/releases/v0.4.29.md](../views/releases/v0.4.29.md). Depends on v0.4.28.

## Goal and authoritative scope

Deliver real Linux, WSL2 and macOS developer workflows while preserving the portable semantics set in v0.4.25 (#872). Host mechanisms belong behind host/runtime adapters. Implementation defects may be fixed with regression evidence; semantic changes need explicit review before v0.4.31 (#174) freezes the contract. This consolidated scope replaces the earlier v0.4.25 assignment, two-PR wording and macOS Local+Remote acceptance.

**Windows:** v0.4 supports the developer path through real WSL2 with Linux `baha`. A native Windows executable/host adapter and Windows containers are outside this release; build-only Windows evidence does not establish native runtime support.

| Platform/use case | v0.4.29 obligation |
| --- | --- |
| Native Linux Docker and rootless Podman | Existing behavior, security and real acceptance preserved |
| Genuine WSL2 | core-821 Dev Local **and Dev Remote** scope remains required; Windows-hosted builds are not WSL2 proof |
| macOS darwin/arm64 | Full Dev Local with **both Docker Desktop and Podman Machine**, real runtime evidence and independent walkthrough |
| macOS darwin/amd64 | Artifacts, native build/unit/conformance where runners exist; runtime support only with its own real evidence |
| macOS Dev Remote and automatic Keychain trust | Explicitly deferred to core-886; not advertised as delivered |
| Developer ID signing/notarization | Explicitly deferred to core-885 |
| Native Windows runtime/containers; Colima/OrbStack/Rancher Desktop | No support claim without separately scoped real evidence |

The macOS deferrals are an explicit delivery decision. Host trust in v0.4.29 is manual: export, documented user action and read-only verified status. Runtime/workload TLS validation stays required.

## Reviewed decisions

- **D1 — observed engine isolation.** `vm-isolated` is a separately reviewed engine classification, not proof of security equivalence to rootless. Keep observed privilege and execution location as separate facts (a rootless engine can run in a VM). Require positive evidence that the selected endpoint belongs to the selected running VM/machine, its owner and access boundary; a context name, executable, socket path, Darwin host or reported rootful status alone is insufficient. Mismatch or unknown provenance yields a typed diagnosis, never a fallback to a privileged host daemon. Validate VM-side filesystem/resource ownership and host bind-mount/file-sharing permissions; VM root must not grant unreviewed access to foreign host paths or engine sockets. Preserve workload policy, user choice and explicit rootful-host opt-in. Owned by core-819; update the pinned engine-selection semantics only after explicit contract review.
- **D2 — effective runtime capacity.** Capacity evidence identifies the selected engine/VM, source, timestamp, applicable limits and quality (measured/estimated/unknown). Physical-host RAM is not effective runtime capacity. `MemTotal` is capacity, not available memory; `MemFree` alone is not `MemAvailable`. `VM MemTotal − sum(docker stats)` is a partial estimate and must not by itself establish SAFE. Prefer non-mutating observations of runtime-visible available memory/pressure and limits; report uncertainty; never turn missing evidence into safe admission; keep the typed admission/remediation model; a policy for explicit user decisions under uncertainty needs contract review; no mutation in plan/preflight. Linux keeps `/proc/meminfo`/PSI and cross-checks engine/VM/cgroup limits (the constraining budget governs); Darwin consumes selected VM evidence; presentation consumes the same result. Owned by core-819/core-820.
- **D3 — one Podman realization.** core-883 executes the existing Quadlet/systemd realization inside the selected Podman Machine VM through a narrow provider-internal executor. No second Compose/kube-play implementation, no generic remote-exec/MCP surface.
- **D4 — four distinct evidence lanes** in core-823: Darwin cross-build, native Darwin conformance, Linux/arm64 container stack, real macOS runtime. Cross-build/native tests cannot replace a container lifecycle proof; the dedicated trusted-trigger self-hosted Mac is core-884. Record actual runner/engine/OS versions and exact sources.
- **D5 — distribution and trust.** core-882 restores Darwin compilation. core-822 adds darwin/arm64 and amd64 packaging, checksums, provenance/attestation subjects, installer and self-update selection. Ad-hoc signing is not Developer ID identity or notarization; verify actual artifacts per architecture; qualify install/update on a clean Mac; observe and document quarantine/Gatekeeper behavior instead of promising a bypass. core-885 owns signing/notarization.
