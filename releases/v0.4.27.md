# v0.4.27 · Remote development and onboarding

Source: [baseharbor#874](https://github.com/mcpdev80/baseharbor/issues/874). Tasks: [views/releases/v0.4.27.md](../views/releases/v0.4.27.md). Epic: [core-777](../epics/core-777-developer-access-and-profiles.md).

## Goal

Deliver one local/remote and solo/team application workflow using native runtime and artifact standards, independent stage versions and readable release inspection; finish remote Node/access/profile experience without becoming a CI/CD platform or overloading the Console release.

## Standards-first operating boundary

[Native delivery, artifacts and stage decision](../decisions/2026-10-18-r27-native-delivery-and-stages.md) is the planning boundary: existing OCI registries/local stores/native transfer; existing release inputs and image metadata; Docker Compose and Podman Quadlet/systemd own runtime behavior. Existing GitHub Actions/GitLab CI build, test, publish and approve releases. Existing Argo CD/GitOps retains delegated desired state/reconciliation; Baha never writes around it. No new CI, registry server, build farm, universal bundle format, pipeline/stage DSL or Kubernetes controller. Runtime feature/version limits are explicit.

## Binding architecture and scope

One selected installation owns authoritative deployment/provider state, identity, consent revisions and mutation locks for its admitted Targets. Management connection and Target are different selections. Local work uses the same semantic core directly without login/server or an unconditional SQL/Secrets/Identity stack; remote CLI/JSON/MCP/HTTP clients address the selected authority, never a connector directly. No authoritative remote state on developer workstations, NFS, home-directory synchronization, Baha-to-Baha federation or new generic state framework.

Portable intent stays in Git. A fresh checkout attaches to an authorized existing application or explicitly registers a new one; the server allocates opaque IDs. Names, URLs and paths alone never confer identity/permission. Candidates are exact selections of existing source/native release/OCI inputs, not a new mandatory package format; build location is explicit and independent from runtime/delivery. Native auth first; protected remote secrets remain within their ownership boundary. The existing core-777 acceptance is preserved, not reduced to the video.

The host task explicitly reconciles current operator-API PostgreSQL/OIDC prerequisites with the capability-first rule; no implicit promise of a dependency-free remote authentication service is made.

## Binding start order and zero-touch evidence (2026-10-22)

**Release-start critical path:** (0) finish v0.4.26 and its cleanup; (1) integrate required Renovate/start updates; (2) accept the evidence contract; (3) implement automatic evidence publisher and read-only resolver concurrently; (4) accept trusted verifier and independently exercise retention/recovery; (5) qualify per-domain CI gates; (6) release the matching implementation slices; (7) perform cross-domain integration, acceptance, docs and release preparation. Independent non-mutating contract/design tasks can proceed alongside steps 2–4 with separate owners. No product task may consume a new CI lane until its own trusted mapping and evidence path are qualified.

**Zero manual evidence burden:** A human contributor, external contributor, Codeman worker or maintainer session uses the same ordinary branch/PR/CI path. Trusted CI automatically generates sanitized bounded result payloads and manifest, records exact source and integration SHAs, hashes and run provenance, publishes append-only evidence to baseharbor-plan, verifies the published payload and updates the task/PR evidence reference using a collision-safe planning change. No manual manifest authoring, evidence copy/paste or special agent-only commands are acceptance requirements. Missing archive or task linkage is visible and fail-closed for any gate that requires retained evidence; ordinary development feedback must remain available and failures must be actionable.

**Security and concurrency:** Untrusted fork PR code never receives write credentials to the planning repository. A trusted post-run workflow fetches artifacts as data, validates provenance, redacts/limits content, and publishes with least privilege. Separate concurrent contributors cannot overwrite manifests or each other's task edits; conflicts retry by re-reading main and using independent PRs/commits. A missing GitHub artifact cannot be reconstructed after expiry; archival must happen while available. Release qualification continues to depend on current trusted plan, required checks and exact SHA rather than archive presence alone.

## Retained CI evidence and multi-contributor execution (2026-10-22)

Before the v0.4.27 CI feature lanes expand, deliver the independent retained-evidence foundation in five bounded stories: [contract](../tasks/t-20261022-r27-evidence-contract.md), [publisher](../tasks/t-20261022-r27-evidence-publisher.md), [resolver](../tasks/t-20261022-r27-evidence-resolver.md), [verifier](../tasks/t-20261022-r27-evidence-verifier.md), [acceptance](../tasks/t-20261022-r27-evidence-acceptance.md). Publisher and resolver can run concurrently after contract acceptance; verifier follows both; independent acceptance follows verifier. Existing v0.4.26 trusted CI is preserved until replacement proof is accepted. No mid-v0.4.26 CI rewrites.

**Resource pool, not a Codeman monopoly:** Codeman coordinator and up to four workers, separate ChatGPT/Codex maintainer sessions, and external contributors can all claim independent tasks. Ownership is a short-lived, visible claim on one bounded write set, not a permanent person/agent lane. Claims record branch, baseline SHA, reserved files, dependencies, review owner and handoff; anyone may take the next eligible task. No two writers change the same authoritative files concurrently; integrate latest main before editing and preserve foreign branches/uncommitted work. Independent reviewers approve trust/coverage changes; authors cannot self-qualify. A coordinator may schedule work but does not reserve all tasks for its workers.

**Parallel sequencing:** After release cleanup and updates, contract stories and existing independent prerequisites may proceed with disjoint owners. The evidence publisher and resolver may run in parallel; architecture/state, access/profile, artifact/stage and node/runtime feature slices run concurrently once their actual interfaces and per-domain trusted checks are accepted. The global ci-lanes task must be delivered as independently qualified domain-specific check increments; do not treat one unfinished global task as a reason to idle unrelated already-covered work. Changes to central CI planner/executor/finalcheck, shared CLI/JSON/MCP/HTTP registration, and final release qualification retain single-writer integration ownership. A contributor may work on an unblocked task regardless of which coordinator or model they use.

**Safety:** Archived existence is not proof of current qualification. Exact source/integration SHAs, trusted run identity, required checks, hashes and independent review remain mandatory. The plan repository is not immutable WORM storage; protected branches, append-only naming, least privilege, redaction and independent backup are required for meaningful durability. Publish only bounded sanitized evidence, not arbitrary full logs.

## Verification and cost boundaries

Contract/docs/profile/identity/locking/journal/packing changes start with deterministic package, HTTP, Git and filesystem tests. Do not run app journeys merely for metadata/schema/UI changes. Native gates uniquely prove actual container/service lifecycle, provider protocol/TLS consumption, reachable exposure, IdP/secret-store behavior or restart recovery; each task states the uncovered property before running it. Docker and Podman are separate affected gates. Independent required gates may run concurrently on isolated appropriate runners; do not consume the K3s runner for Docker/Podman.

No task automatically launches a full pre-release matrix. A failed overall run does not discard other green receipts: reuse only when the existing verifier authenticates compatible exact inputs and no newer relevant negative supersedes them; rerun failed/affected coverage. Missing/failed/skipped/unverified requirements remain open, not PASS. Final complete pre-release approval, promotion and publication remain separately authorized recurring cards.

The first promotion proof is deliberately small: one app, two environments, exact existing images in native stores or one controlled OCI registry. It follows accepted prerequisites and reuses adapter proofs; it does not require optional registry provisioning or live GitOps. Enterprise auth/private-CA, registry-free transfer and other required cases remain final acceptance, not deferred scope. Application migration responsibility is normative in candidate-contract/product specifications and explained by docs.
