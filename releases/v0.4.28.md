# v0.4.28 · Console, Grafana OSS and management workflows

Source: [baseharbor#875](https://github.com/mcpdev80/baseharbor/issues/875). Tasks: [views/releases/v0.4.28.md](../views/releases/v0.4.28.md).

## Goal

Deliver genuinely usable Console journeys, not only a login or a working UI container. The Console stays an optional client of one selected management Core, never a second authority.

## First engineering priority — CI shard result reuse (critical)

- [Green Go shard reuse](../tasks/t-20261109-r27-ci-go-shard-reuse.md) is the first development task of v0.4.28, immediately after required cleanup and Renovate intake and **before** Console implementation. Preserve its historical stable card number.
- Reuse authenticated, unaffected green CLI and package shard results across successive commits within one PR; rerun only the impacted tests and native gates with strict dependency/fixture/plan SHA verification.
- No new CI framework, evidence approval chain, or blanket full matrix; keep PR Selected Checks fail-closed on unknown, missing, failed or stale evidence.

## Work area 1 — Console backend and domain integration

- Authenticated one-Core connection, proper RBAC/ownership and the shared Core/Target application API.
- Expose all permitted visible local/remote Targets; application lifecycle, logs/events, status/doctor, safe mutation and useful evidence through existing Core/domain interfaces.
- Bridge core-777 onboarding/authorization with the Console; no duplicate provider or Target state.
- Owns Console backend/API integration and server-side adapters.

## Work area 2 — Console frontend and UX acceptance

- Guided app create/edit with the same capability checklist/compact footprint preview as the CLI.
- Target selection, repository/workspace management where supported, app operations, logs/events, actionable failures and verification.
- Full independent login → choose Core/Target → deploy/edit/inspect → remove/offboard journey; EN/DE docs.
- Owns Console UI and web UX tests, not backend authority.

## Binding scope expansion — Grafana OSS (Owner decision 2026-11-13)

The **complete Grafana OSS visualization integration** (historical candidate #166) is part of v0.4.28, **not post-v0.5**. This replaces and removes all Grafana deferral language from `core-209`. Delivery includes optional managed installation and lifecycle, secure access, provisioned Prometheus/Loki/Tempo data sources, real monitoring dashboards, native Grafana OSS alerting/routing, Console monitoring entry/context links, end-to-end Docker and rootless Podman tests, and EN/DE documentation. Grafana remains optional per installation and is never an implied application capability or a mandatory dependency of minimal deployments. A complete integration is required when enabled, not merely a static link, demo, or partial dashboard.

Monitoring must distinguish available telemetry from absent collection. Use existing metrics/logs/traces and provider ownership; do not create a parallel telemetry/monitoring database or collector. Grafana alerts must be real, bounded and provisioned through supported OSS APIs, with tenant/Target scope and secret-safe contact points; no invented alert coverage or unapproved external notification service.

## Provider Contract and dashboard dependency rules (binding)

- **0428-032 is the Grafana architecture gate:** `IntegrationDescriptor.Validate` currently requires a real application capability, so Grafana MUST be modeled as an optional provider-owned management/visualization tool through a compatible Provider Contract v1 extension or existing management interface; never falsely implement `metrics`, `logs`, `traces`, or change portable application intent.
- **0428-033 inventories actual produced/collected series, labels and provider ownership** before dashboard or alert selection. An installed provider is not evidence that an exporter or all required metrics exist.
- **0428-034 chooses dashboard templates only when their real query prerequisites are satisfied** by authorized selected Target/provider instances. Existing community templates are curated sources, not auto-enabled, authoritative or guaranteed to work unchanged.
- Verified candidates: [Node Exporter Full 1860](https://grafana.com/grafana/dashboards/1860-node-exporter-full/) (requires Node Exporter), [Docker monitoring 15798](https://grafana.com/grafana/dashboards/15798-docker-monitoring/) (requires cAdvisor metric and label compatibility), [PostgreSQL 9628](https://grafana.com/grafana/dashboards/9628-postgresql-database/) (requires postgres_exporter), [MongoDB Replica Set 25802](https://grafana.com/grafana/dashboards/25802-mongodb-replica-set-full-overview/) (requires Percona mongodb_exporter and matching metrics), [RabbitMQ Overview 10991](https://grafana.com/grafana/dashboards/10991-rabbitmq-overview/) (requires RabbitMQ Prometheus plugin-compatible data). All are **conditional**; do not add privileged exporters or show empty dashboards as deployed/healthy.
- **0428-035, 036, 037** are independently writable host/container, database and messaging template tasks after 034. Existing native BaseHarbor infrastructure dashboard 012 and logs/traces dashboard 024 use real signals. Dashboard JSON/import version/UIDs must be pinned, tested, and scoped to existing metrics/logs/traces.
- **Do not over-serialize:** Provider Contract (032) and current metric inventory (033) can run independently after release start. Grafana runtime (010) depends on 032, NOT Console audit 008. Grafana datasource workers 011/022/023 can then work in parallel in disjoint files; dashboard and security workers can proceed on their actual prerequisites. Console UI cards proceed independently after Console adapter 009. Grafana native proof 030 and Console journey 018 are separate. One Coordinator schedules up to five non-overlapping workers; Codex reviews and merges.
- Each card explicitly identifies exact source entry points or requires the worker to inspect current source and stop on a missing contract. Preserve targeted CI routing and exact-SHA evidence.
