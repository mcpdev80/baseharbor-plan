# v0.4.30 · Simplify TLS and strengthen attack protection

Source: [baseharbor#904](https://github.com/mcpdev80/baseharbor/issues/904). Parent roadmap: #427 · master: #155 · milestone v0.4.x. Tasks: [views/releases/v0.4.30.md](../views/releases/v0.4.30.md).

## Goal

Before the pure final acceptance in v0.4.31 (#174), implement and qualify the bounded TLS/proxy and attack-protection changes.

## Scope

- [core-902](../epics/core-902-native-tls-justified-proxies.md) — native TLS/mTLS first; single proxies only with justified added value; keep required routing/HA/auth.
- [core-903](../epics/core-903-attack-protection-ddos-boundaries.md) — attack-protection baseline and clear operator/upstream DDoS boundaries.

**Cut both epics into small tasks with their own result, acceptance and PR against `develop` (core-888) before implementation.** No shared monolithic implementation PR. Moving the release assignment is planning, not delivered protection. No tasks are cut yet.

## Acceptance

- The native TLS/proxy rule is anchored in the existing provider/security specification and conformance; exceptions are justified.
- Selected changes to existing realizations preserve auth, trust, rotation, consumer contracts, isolation, lifecycle and recovery; actual provider/single/HA combinations are evidenced.
- Agreed abuse/resource limits, trust boundaries and internal/admin exposure are qualified with small negative tests; claimed protection and externally assumed protection are distinguishable.
- Necessary Docker/rootless Podman/ecosystem evidence and EN/DE documentation/release notes are current; valid green evidence from partial or failed overall runs is reused after verifier checks.
- Changes stay provider/operator/runtime realization where sufficient. Actually missing portable semantics are reviewed explicitly; no blanket new contracts or security profiles.

## Ordering and boundaries

Qualify/promote v0.4.29 → v0.4.30 → **v0.4.31 (#174) pure final semantic acceptance**, then the stability reconciliation and the v0.5 (#175) freeze. #174 checks the delivered base; it gets no additional implementation epics. Newly found real defects still must be fixed; concrete security gaps are not deferred only because of this plan. No extension of active v0.4.25/v0.4.26 acceptance; no authorization for full pre-release, merge, tag or publication.
