## v0.5.0 goal (#175)

Freeze and stabilize the runtime-neutral BaseHarbor language and semantics completed in v0.4. v0.5 adds no new platform primitive, runtime or major capability. Frozen model: Portable Intent → Environment + Policy → Capability/Provider Resolution → Placement/Ownership → Plan/Preflight → Provision/Bind → Observe/Reconcile → Verify → Audit/Evidence. Compose stays the complete reference runtime; Kubernetes consumes the frozen semantics later.

**Compatibility question — v0.5 is ready only when the answer is yes:** can a later runtime provider, including Kubernetes, implement the frozen semantics without a fundamental rewrite of the portable application contract? (No Kubernetes implementation in v0.5.)

## v0.5.0 scope

Contract/schema versioning; capability-spec versioning; capability-provider protocol compatibility; machine result/error schema versioning; persisted state compatibility/migration rules; deprecation rules; upgrade compatibility from supported v0.4 state; full security/ownership review; documentation reconciliation; exact-head conformance/acceptance; packaging/release hardening; release artifacts and metadata consistency.

## Rules

- **Developer experience:** the normal path stays `git clone → cd → baha app init → baha up`; no migration ceremony without demonstrated need; simple final pre-freeze defaults; v0.5.0 is the first frozen compatibility baseline; no migration/deprecation ceremony for obsolete pre-freeze-only behavior; CLI/JSON/MCP stay adapters over one core; no runtime/provider detail in portable intent.
- **Agent-native Compose completeness:** the agent-native lifecycle was implemented before the freeze (#403, closed). Revalidate that a generic coding agent can operate the supported lifecycle (discover → inspect → plan → apply/up → status → doctor → observe diagnostics → update → backup → restore → drift/repair → destroy, where supported) without raw shell/Docker/Compose/Podman, through a small semantic API over the shared core; no 1:1 CLI mirror; safety metadata, confirmation/approval, policy, ownership, preflight, reconciliation, verification and evidence cannot be bypassed; secret-safe output; smallest useful observability surface; unsupported operations fail explicitly.
- **Explicitly deferred:** availability/HA/topology semantics; Kubernetes runtime; Operator/CRDs; OpenShift/enterprise runtime; operator/human OIDC, RBAC, JIT and breakglass (core-100); private-registry/air-gap implementation; optional ecosystem breadth.
- **Core freeze rule:** post-v0.5 core changes require a genuine missing platform primitive; product-, runtime-, IDE- or vendor-specific shortcuts never justify contaminating portable semantics.
- **Kubernetes readiness without Kubernetes fields:** three explicit layers — portable application intent (what it needs), deployment/operator state (where and under which conditions), runtime/provider realization (how). Target/Access/Scope (#408) is frozen and revalidated, not reshaped: Deployment = Target + Application + Environment; Target references Runtime Provider, Access Reference and Scope. Access stays a secret-safe reference outside portable intent; credentials are never migrated into portable state; provider-native auth stays behind the Runtime Provider. Platform resource references (shared ingress/gateway, storage policy/class, namespace/project, platform identity/trust, policy/profile) stay opaque/runtime-owned; no `GatewayClass`, `StorageClass` or `namespace` in portable intent. The result model distinguishes supported, unsupported, unverifiable, denied/not authorized, conflict, foreign-owned, degraded and failed verification so a restricted runtime fails only the affected feature.
- **Existing target scope semantics:** a Target may point at an existing platform-named scope (e.g. Kubernetes namespace `r2-4b-dt-test`, ownership platform/external). The runtime provider interprets the scope; BaseHarbor never renames or recreates a platform-owned scope; several applications may share one namespace if policy allows, so ownership is tracked below namespace level by stable identity; `baha destroy` removes only BaseHarbor-owned resources and never deletes a platform/external namespace; namespace deletion only when explicitly BaseHarbor-owned and allowed.
- **Capability compatibility is semantic, not nominal:** a provider is not compatible merely by advertising the same capability ID; a versioned way to express and negotiate required semantics exists when the default contract is insufficient; normal intent stays sparse; absence means the default/common semantic; only demonstrated non-default requirements become explicit; no provider details in intent; feature compatibility is separate from availability/topology guarantees; a missing required semantic is unsupported, not degraded success.
- **Delivery boundary:** runtime ≠ capability ≠ delivery; direct and delegated delivery, explicit reconciliation ownership, typed delivery/synchronization states, placement where applicable, provider-neutral desired revision identity; no Argo CD/Flux/Git-provider/Helm/Kubernetes fields in intent. A real GitOps provider comes later (core-325).
- **Provider Catalog and descriptor freeze:** Provider Catalog (what implementations exist and can be resolved) ≠ Provider Runtime Registry (what instances are installed/running/bound; stays authoritative). One catalog model for RuntimeProvider, CapabilityProvider and DeliveryProvider families. Descriptor fields at least: family/kind, stable provider ID, implementation version, Provider Protocol compatibility, supported service/capability contract versions, protocol/capability declarations, platforms, OCI artifact reference, authoritative content digest, schema/descriptor version, provenance/signature references. Distribution reuses OCI standards; digest identity is authoritative and tags are human references; JSON Schema 2020-12 where applicable; Baha extensions versioned and minimal. No marketplace, hosted registry or search UI in v0.5.0.
- **Runtime-provider freeze prerequisite:** do not freeze the Compose-coupled transitional seam; #396 (closed) complete; the runtime-provider boundary stable enough to version as v1; Docker and Podman prove it as reference implementations; no runtime products required in portable Core semantics; adopted standards vs extensions documented.
- **MCP completion:** v0.5.0 freezes and validates an already complete, continuously maintained agent-native contract (#397, #398, #403 and the parity gates of later v0.4 releases); prove the final v0.4 semantics are consistent across CLI, JSON and MCP.
- **Pre-freeze compatibility rule:** v0.5.0 freezes the final converged contract and promises no migration from obsolete pre-freeze development formats or command shapes: pre-freeze v0.4 converges freely → v0.5.0 establishes the baseline → v0.5.x+ versions/migrates/deprecates from frozen contracts. No legacy modes, aliases, state migration layers or shims for earlier v0.4 shapes.
- **Developer access prerequisite:** the freeze must not begin until core-777 is complete (no mandatory login for local development; standards-first Git/SSH/kubeconfig/cloud auth; explicit temporary vs secure persistence; recoverable secure local credentials; strict separation of profile export/import, application recovery and platform DR).
- **Standards-first prerequisite (comments 2026-09-23):** core-390/#391 settle the service/binding/provider boundaries first. Do not lock in accidental identities (cache == Redis, object-storage == S3, observability == OTLP, identity == a concrete IdP). JSON Schema 2020-12 is the canonical schema dialect; Service Binding 1.1 names are authoritative where applicable; service vs protocol vs provider vs product/version axes are frozen separately; catalog metadata is distinct from runtime instance registry state; current v0.4 capability IDs have explicit compatibility/migration classification; OTel/OIDC/AsyncAPI/CloudEvents/RESP/S3 compatibility is correctly located. Existing v0.4 IDs stay compatible until migration is tested; v0.5 freezes the resolved model, not an unreviewed rename.
- **Freeze-boundary clarification:** v0.5.0 freezes the complete semantics; the v0.5.x line hardens versioning/compatibility. The freeze starts from a v0.4 where these are real behavior: trustworthy convergence; observable/reconcilable artifact drift; no stale successful workload after source changes; provider-neutral intent (logical capability first); transparent provider/runtime realization; guided init + `baha up` as the canonical path; CLI/verbose/JSON/MCP from one truth. Freezing does not hide provider information; it prevents products such as PostgreSQL from becoming the portable contract. #175 freezes the boundaries/inventory; core-297…core-300 version, migrate, formalize compatibility, upgrade/recovery/deprecation and prove the model.

## v0.5.0 acceptance

### Release gates
- v0.5.0 explicitly establishes the first frozen compatibility baseline without requiring migration from obsolete pre-freeze-only state.
- Portable/deployment/runtime/provider state boundaries are documented.
- Structured machine-output schemas are versioned.
- Capability-provider contract/conformance is documented.
- Security and ownership review passes.
- Human CLI, JSON and MCP demonstrably use shared domain/lifecycle logic.
- A generic coding agent can complete the supported Compose lifecycle end to end through BaseHarbor MCP/JSON without raw shell/Docker/Compose fallback.
- Machine/agent coverage includes discover, inspect, plan, apply/up, status, doctor, update, backup, restore, drift/repair and destroy wherever those lifecycle operations are supported by BaseHarbor.
- MCP remains a small semantic surface and does not become a 1:1 CLI wrapper or generic runtime-execution interface.
- Five-minute onboarding is validated from a clean environment.
- Canonical documentation matches actual behavior.
- The exact final implementation head is validated economically.
- Local/repository validation is used first where practical; GitHub Actions only where required.
- Human-friendly release notes exist.
- Changelog, tag, source and release metadata agree.
- Release artifacts are verified.

### Pre-freeze architecture gate
The public contract is not frozen until the v0.4.31 acceptance has explicitly closed these boundaries. The gate is about contract sufficiency, not ecosystem breadth: it does not require pgAdmin, Keycloak Admin UI, Valkey Admin, Grafana, AI, vector search, Kubernetes, cloud providers, air-gap support or other optional integrations beyond the scheduled pre-freeze capabilities (#516). A genuinely missing portable primitive is fixed before the freeze; product-specific tooling is deferred.
- Managed application identity/authentication boundary (#363).
- Secrets and credential ownership boundary.
- Network/connectivity and exposure boundary.
- Storage/state ownership boundary.
- Artifact/distribution and supply-chain identity boundary.
- PKI/certificate/trust lifecycle boundary.
- Backup/restore/recovery semantics.
- Audit/evidence semantics.
- Ownership and placement semantics.
- Runtime/capability/delivery separation.
- Workload-source / repository-adoption boundary (#519).
- CLI/JSON/MCP semantic parity.

### Target contract freeze
- Target state remains deployment/operator state, not portable application intent.
- Target-scoped runtime/deployment state from #408 is part of the persisted compatibility surface.
- Changing Target never rewrites portable application intent.
- Runtime Providers consume the resolved Target contract rather than redefining it.
- CLI, JSON and MCP preserve the same effective deployment identity.

### Runtime access compatibility
- Access remains referenced outside portable application intent.
- Credential material itself is never migrated into portable application state.
- Provider-native authentication details remain behind Runtime Provider interpretation.
- Compatibility/versioning applies to persisted Access metadata where BaseHarbor owns it.

### Provider Catalog freeze
- Provider Catalog and Provider Runtime Registry are documented as separate boundaries.
- One catalog contract can describe Runtime, Capability and Delivery Provider families without merging their responsibilities.
- Provider descriptors are versioned and machine-validatable.
- OCI artifact reference + digest are part of the frozen provider distribution identity.
- Catalog metadata does not become portable application intent.
- Existing provider instance/binding/ownership state remains authoritative runtime state and is not duplicated into the catalog.
- No proprietary BaseHarbor artifact transport/package format is required for provider distribution.

## Standard pre-release gate

Applies to v0.5.0 and to every v0.5.x, v0.7.x and v0.8.x patch release whose source issue carries it (#175, #297–#300, #102, #304–#310, #313–#320, #325). Acceptance answers whether the scope is complete; this gate answers whether the exact commit is safe and documented well enough to release. Do not weaken or skip a required check to complete a release; record genuinely not-applicable checks instead of omitting them.

- All acceptance criteria of the release/task are complete.
- Required local/repository tests pass.
- The full relevant CI matrix has passed at least once on the exact release-candidate commit.
- Docker and Podman acceptance pass where applicable.
- Security, isolation and secret-leak checks pass where applicable.
- The documentation audit defined by #364 passes.
- Human-facing documentation matches the shipped behavior.
- Reference and normative specs match every changed public contract.
- No unresolved release blocker remains.
- Version, changelog, release notes and release metadata are consistent.
- Final exact-head acceptance evidence is recorded before tagging/releasing.
