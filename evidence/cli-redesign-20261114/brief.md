# CLI redesign – owner working brief

Owner request, 2026-11-14. This is a planning snapshot, not proof of implemented features or a blanket approval of every proposed name. The authoritative engineering rules are the Core `AGENTS.md` and `docs/DEVELOPMENT_GUIDELINES.md` on the actual implementation base. The existing umbrella card is `t-20261114-r28-cli-command-semantics`; v0.4.28 startup dependencies remain in force. See [old-to-new map](command-map.md) and [static code entry index](code-entry-index.md). Existing developer-owned work and the archived Console/Node Connector public repositories remain outside scope unless specifically reauthorized.

## Owner decisions

- Smallest guided workflow: clear short English CLI; no interactive dead ends. Blank/missing input offers a task-specific wizard, arrows/Enter and Tab where appropriate; cancellation preserves state. `--no-input` and scripts never block and get typed actionable errors. Setup completion once persists; active context is per terminal only.
- Stable meanings: `app plan/up/down` are frequent, `app pull` updates Git sources, `--up` invokes the same app-up operation; `-t` target, `-e` environment, `-c` one or comma-separated components throughout applicable commands. Names and meaning must be consistent. Current app apply/up and app/workspace updates differ; unify real semantics, never just relabel.
- App source is a Git repo, local directory or supported OCI source; components are optional and unique per app, multiple per source; pull impacts the entire Git repo, with preview of shared impacts. No accidental neighboring-repo scan. Current directory as project default; other directory path guidance starts at home with shell Tab support.
- `app setup new` greenfield and `init` brownfield; no separate human config-only create path, but preserve underlying domain/MCP operation. `app setup env` associates a shared environment, creates if needed, edits app-specific settings or detaches without deleting the environment. `app exec -c backend` shell, `--cmd` command; `app status` whole app and components, `-c` filters; urls lists actual app/shared-service GUIs. Existing show/footprint/preflight/evidence functionality must be preserved at target locations.
- `app data env` app variables; `app data secrets` app-managed secrets with optional arbitrary type; `app data services` complete bound service connection data, including credentials. Reveal defaults masked; explicit `--reveal` can show selected or all authorized values. App secret list supports single named selection and reveal. OpenBao protection and audit apply to all access paths; no plaintext in manifests, logs, audit or normal machine output. `app data tls` guided; backup/restore distinct from selectable encrypted export. Audit actual access/changes/denials when enabled, never values; no personal attribution without person identity.
- Environment names are unrestricted by fixed `dev/test/prod` semantic special cases; same capabilities irrespective of name, behavior follows explicit policy/authorization. Initial local context is guided/automatic, no hardcoded `dev` rule and no account required when local access allows. Environments, apps and targets each have stable IDs; deployment IDs remain separate. Environment is shared by multiple apps and multiple nodes/future clusters; an app may be in multiple environments. Distinguish environment/target/app identity; no implicit shared data/credentials.
- Environment create/edit/delete guided; protected edit/delete require authentication and authorization as configured. Delete previews environment-scoped deployments and consequences; choose `Keep data` (default) or `Delete data`, explicit final consent, no forced prior per-app detach. Shared app identities, other-environment deployments and nodes persist. Unknown ownership/impact fails closed; do not promise retention/restore without real verification. Company `organization.yaml` can distribute environment declarations in the future; reconciliation/authority/versioning need a contract.
- User expressly wants nonsecret `app.id` committed in versioned `baseharbor.yaml` and generated at new/init, reused by another checkout/Core, no manual UUID request; preserve historical ID and reject conflicts. Current generated authored YAML omits ID; this changes portable contract and must be versioned/migrated, coordinated with Core and Git authority. Names and URLs alone are not authorization.
- Proposed top-level taxonomy: `app`, `env`, `target`, `context`, `platform`, `access`, `system`. Platform local/remote/node; access separates user, workstation, grants and login; external provider registration is not provider authoring. `target delete` today detaches configuration and preserves data; proposed `target remove` retains that. Root `destroy` is whole installation, not app destroy.
- Protected operations follow plan -> preflight -> apply -> verify. Separate actual Core, Target, environment and workstation identity; authorization is not identical to an optional extra reveal password. CLI, JSON, MCP/HTTP share semantic core and safety, with human-only sensitive reveal deliberately excluded from ordinary machine output. No additional dynamic product CLI requirement; retain existing SQL/cache and make unsupported capabilities explicit.

## Mandatory validation and planning limits

New code and tests must follow product AGENTS, development guidelines and test-to-CI routing in plan AGENTS. Owner-authorized maintainer acceptance is not an independent review; prove actual exact-SHA checks and native tests when affected. No full release/tag/promotion authorized. This snapshot contains proposed command names with unresolved decisions (organization/Core source of truth and policy inheritance, env data retention/restore, fresh vs existing authentication, safe compatibility period and fork/multi-Core behavior). Resolve via contract task and owner before implementation; do not invent behavior. All cards are planned/unassigned and blocked by explicit dependencies; coordinator serializes shared write sets and assigns at most five ready workers. Implementation stays in Core; planning is direct-main with render/check and normal concurrency-safe push.
