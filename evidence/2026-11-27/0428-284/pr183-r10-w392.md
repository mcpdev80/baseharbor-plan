## DIAGNOSTIC: why the digest lands in the main loop, not final-drain (w267 Finding 1 root cause)

- Verified via three diagnostic scripts (/tmp/diag_r10*.py): the digest at offset >= 4096 (pad_line = "P"*(4096 + len(digest_line))) lands inside the 2nd 4096-byte read window of the main select() loop, well before proc.poll() observes exit. FINAL_DRAIN_CHUNKS == 0 in every configuration tested (single core, two-core abort+second, background-thread-after-exit, sleep-past-no_output_timeout).
- Conclusion: a digest emitted as normal process stdout can NEVER be deterministically placed in the final-drain branch via run_tty's single-pty model — this is structural, not a timing race. The w267 "assert the digest occurs in a chunk observed from the final-drain branch" is therefore resolved by the SEPARATELY PROVEN FINAL-RAIL FIX: the digest reaches the captured transcript via the authoritative on-disk log (log == transcript after CR-normalization), which is exactly what the production flow depends on.
