## Findings

**CODEX-REVIEW: REQUEST CHANGES.** Two runtime blockers persist at the refreshed candidate.

1. `PersesComposeServices` in `internal/serviceaccess/perses_gateway.go` passes `--config=/etc/perses/config.yaml`, but does not render or mount that file into the Perses container. The `PersesGatewayPlan.Policy` values (authentication, encryption key, allowed schemes and denied networks) therefore are not applied to the Perses process. Existing tests validate the plan and inspect rendered arguments but do not prove the security configuration reaches Perses.
2. `BuildPersesGateway` sets `UpstreamBindAddress` to `127.0.0.1`; the separate gateway targets `http://perses:8080` across the Compose network. Perses loopback belongs to its own container network namespace, so the gateway cannot reach that listener. The source contract and renderer test both currently enforce the unreachable address.

## Required correction recipe

1. Render deterministic Perses config from the validated security policy and mount it read-only into the Perses container; include credential file references without interpolating or logging secret values. Add a rendered-runtime assertion that checks the actual file/mount and the consumed settings.
2. Bind Perses on its private Compose interface (or deliberately share the gateway network namespace), keep Perses unpublished to the host, and preserve the gateway as the only host-visible endpoint.
3. Add/run an isolated integration check proving gateway-to-Perses reachability, authentication enforcement, proxy restriction and HTTPS. Then publish normally, observe fresh exact-head CI, and request a new review. Stop if config provenance or private-only reachability cannot be demonstrated.
