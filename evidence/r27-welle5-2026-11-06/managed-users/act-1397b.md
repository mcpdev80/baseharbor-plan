## Blocking findings

1. **Create-fallback does not bind the resolved account to the create response.** In `managed_user_invite.go:createManagedUser`, the fallback GET record is accepted by `managedUserOwnedIdentity(users[0], email)`. That predicate checks the email/username, enabled state, managed-invite marker and absence of credentials, but never compares `users[0].ID` with `created.ID` from the successful POST response. The code comment says it matches the create result by ID, but the implementation does not. The fallback regression only returns a wrong-scope `developer-access` record, so it does not cover a different ID carrying the same email and managed-invite marker. This leaves the prior foreign-account adoption concern unresolved for an ID-only create response.

2. **The ambiguity mutant is a separate handwritten flow, not a production-source mutation.** `managed_user_invite_mutant_test.go` calls production in its guarded subtest, but that control can still pass if the `len(users)>1` guard is removed: the fixture records do not satisfy the later ownership predicate, which independently returns an error. Its red subtest calls `inviteManagedUserMutant`, a separately implemented helper that skips the production resolver and sends activation directly. It therefore does not show that removing the actual production ambiguity guard makes the regression fail. This is the same unresolved mutant-evidence gap called out by review-1397a.

## Correction recipe

- In the POST-201 fallback, retain the returned create ID and require the resolved record ID to match it before any activation. Keep the email/username, enabled, `baseharbor.scope=managed-invite`, and credential checks. Add a regression where POST returns ID `u1` and fallback returns a different ID with the same email and managed-invite marker; assert refusal and no activation. Also retain the existing wrong-scope fallback control.
- Replace the handwritten `inviteManagedUserMutant` demonstration with an actual source mutation of the production `len(users)>1` guard in an isolated worktree. Run the same production-path regression against the mutated source and record RED, then restore the source and record GREEN. The restored candidate must remain green.
