## Seven review points

1. **Changed-content duplicate rejection — FAIL on the production request path.** The store index is keyed by `operationID`, and `handleExecute` maps `request.OperationID` through `operationByID` then calls `create(operation.ID, actor, request.Context)`. Here `operation_id` selects a supported semantic operation (such as `status`); it is not a unique request/idempotency key. `request.Input` is copied only after `create` and is not part of the stored commitment or comparison. Therefore two legitimate requests for the same operation and context collapse to the same journal entry even when input differs; an input-only mutation is silently treated as reconnect. A changed context gets a typed `machine.ErrorValidationFailed` in `create`, but the unchanged handler wraps that error as `machine.ErrorInternal`/HTTP 500. The new tests exercise only direct store calls with operation strings `charge`/`refund` and change `OperationContext`; they do not exercise the HTTP request shape or input mutation.
2. **Reconnect — FAIL after journal reopen.** The new test reconnects only against `newExecutionStore()` (memory). `load()` restores records including `OperationID` but never reconstructs `operationsIndex`. An independent exact-SHA persistent probe showed: first create -> close/reopen -> same operation/context returned a different ExecutionID and added a second journal line (`same_id_after_reopen=false`, lines 1→2, records=2). A fresh reopen followed by the same operation ID with changed context was accepted as a second execution (`changed_duplicate_after_reopen_rejected=false`). Same-process changed-context rejection left its journal at one line, but that persistent no-side-effect check is not in the permanent tests.
3. **Persistence before effects — PARTIAL.** Store creation appends and syncs the accepted journal line before returning, and `handleExecute` calls `create` before launching `runExecution`. Existing durability probes verify failed append prevents state/event publication. I did not find a test that observes the execution callback/effect only after the accepted request commitment is readable from the journal; current tests assert store state or absence of an event after forced failure, not the executor ordering.
4. **Bounded retention / no secret or progress payload — PASS for the journal format.** The persisted entry stores identity, operation, actor, context, state and timestamps, not result/progress/error payloads. Existing `TestRound3BoundedRetentionAndNoPayloads` exercises 6,000 operations, checks the 16 MiB aggregate bound and scans secret-laden result data out of journal segments. The new in-memory index contains IDs only. The full package suite passed.
5. **No exactly-once-across-crash claim — NO explicit cross-crash guarantee, but wording overstates the demonstrated behavior.** The new comment says a reconnect is “replayed once, never a second time,” and a test comment says “the operation is replayed once.” There is no explicit exactly-once-across-crashes wording, but this unqualified promise is contradicted by the reopen probe and the store does not itself execute/replay work. Narrow this to returning an existing accepted execution within the supported retention/recovery semantics; explicitly disclaim exactly-once external effects across crashes.
6. **Write-set — PASS.** The exact diff touches only the bounded `internal/machinehttp` store and two tests; no `cmd/baha`, `internal/delivery`, or `.github` path is changed.
7. **Package tests/build/gofmt/vet — PASS locally; hosted selected checks remain open.** From an archive of exact SHA `0ce814d0`: `GOCACHE=/tmp/codex-review-1373a-gocache go test ./internal/machinehttp` passed (28.8s); `go vet ./internal/machinehttp` passed; `go build -buildvcs=false ./internal/machinehttp` passed; `gofmt -d` on all changed Go files produced no output. ## Verdict: REJECT

### REZEPT

- `internal/machinehttp/store.go`: do not use the semantic operation selector as an idempotency key. Establish a unique per-request operation identity and persist a non-secret commitment over the full authorized request (operation, actor, context and a safe digest of input); reject a reused request identity with a changed commitment before appending or scheduling effects. Keep raw input, results and progress out of the journal.
- Rebuild the operation index from the retained journal during `load()`. Add permanent disk-backed tests for same-request reconnect after reopening (same ExecutionID and unchanged line count) and changed-content reuse after reopening (typed rejection, unchanged line count and no second record). Also assert a normal new request for the same semantic operation remains possible with a fresh request identity.
- Update the owning request integration so duplicate/reconnect outcomes are distinguishable from a newly accepted execution: do not start another `runExecution` for an existing record, and surface the typed validation error rather than wrapping it as internal. Respect the later journal-wiring card's ownership when assigning these handler changes.
- Add an ordering regression that instruments the executor/effect callback and confirms the committed journal record can be read/reopened before any effect starts. Keep the existing append-failure/no-event and bounded-retention/no-payload coverage.
- Narrow “replayed once, never a second time” comments/tests to the actual bounded guarantee and state explicitly that exactly-once external effects across crashes are not promised.
- Required recheck at corrected SHA: duplicate-input and reconnect probes in memory and after reopen; prove rejection has no second journal line or executor attempt; run focused package tests, build, gofmt and vet; mark the PR ready and observe the selected CI jobs before claiming those gates.
- Stop/reject if the public semantic `operation_id` is still used as a per-request dedupe key, any reconnect after reopen creates a second execution, changed request input is not detected, or effects can begin before the accepted journal commitment is durable.
