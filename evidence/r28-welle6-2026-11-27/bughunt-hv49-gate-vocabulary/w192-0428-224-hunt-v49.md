## Findings

### F1 (drift, both directions) - release-requirements.json has 3 gates absent from coverage catalog

File: `scripts/release-requirements.json`, gates array.
Lines: the three entries are registered in `required_for` with release versions but have NO row in `scripts/pr-gate-coverage.json` `gates` array (compare `req_ids` (66) vs `cov_ids` (63)).

Missing from coverage catalog:
- `integration/docker/remote-target`
- `integration/podman/remote-target`
- `integration/static/live-console`

Effect: These three are the "archived Console/Connector acceptance" gates. `release-requirements.json` still lists them (with release versions), but the declarative coverage catalog that `pr-gate-plan.py` / `pr-native-gate-plan.py` actually consults does not declare them, so they are silently dropped from every gate-selection run. The validator (`validate-pr-gate-coverage.py`) does not flag this: `missing`/`extra` checks are scoped to the PR's active release (v0.4.27), and these gates are not required for v0.4.27, so the mismatch is invisible to the validator.

This is NOT a bug in the current state: `scripts/test_ci_v0427_gate_catalog.py` (test_v0427_requires_every_active_scope_gate, test_full_v0427_catalog_selects_without_gap) explicitly asserts these three are `archived_consumer_gates` and must NOT be in the v0.4.27 selection. So the drift between the two catalog files is intentional and regression-tested. The finding is a VOCABULARY-HEALTH note: the two catalog files disagree on the membership of these 3 gates, and nothing asserts that `release-requirements.json` `gates` == coverage-catalog `gates` as a set. A future release bump of any of these three in `required_for` would silently stop flowing into any runner without tripping a check.

### F4 (draft/ready transition effect on gates) - #1842/#1843/#1844 toggle incidents

Repro material / current state (READ-ONLY):
- ci.yml `on:` pull_request triggers: `types: [opened, synchronize, reopened, ready_for_review, converted_to_draft]` (line 14).
- Every blocking job carries `draft == false` in its `if`: confirmed for pr_native_impact (line 34 uses `draft == false`), pr_native_selected (line 529), pr_plan (line 479), pr_validations, pr_focused, pr_selected_final (line 1502), source_format, and the main branch gate (line 605/654/678 `draft == false`).
- The regression `test_workflow_tests_ready_updates_without_duplicate_develop_push` (scripts/test_pr_ci_fallback.py:270) asserts exactly this: `{'synchronize', 'ready_for_review'} <= set(trigger['pull_request']['types'])` and `draft == false` in the four named jobs + native impact/selected.
- There is NO gate-logic that reads draft state beyond the `if` guard. `scripts/pr-gate-plan.py` and `scripts/pr-native-gate-plan.py` do not reference draft at all; the plan is recomputed fresh on every `ready_for_review`/`converted_to_draft` re-trigger because pr_native_impact checks out the trusted develop policy ref and recomputes the matrix from the changed-path diff.
- Draft gating is a CI-job `if` gate (github event context), not a release-gate catalog entry. There is no `integration/static/draft`-style gate and the mission forbids inventing one. So the #1842/#1843/#1844 draft/ready toggles have a single, well-documented effect: they re-run the same planner (draft==false only), no gate vocabulary is added or removed on toggle.

Drift note (F4): no drift. The draft toggle is fully covered by the existing `if` guards and the ready-coverage regression. The only vocabulary surface that could have been affected (a draft-aware gate token) does not exist and must not be invented.
