## Findings

### F1. Runtime PostgreSQL config: inconsistent default-vs-required handling (config quality)

- file: `internal/runtime/config.go:59-67` — `port("BASEHARBOR_POSTGRES_PORT")` and `port("BASEHARBOR_OPENBAO_PORT")` require a valid TCP port (no default; empty => "BASEHARBOR_POSTGRES_PORT is required").
- file: `internal/runtime/config.go:69-80` — `BASEHARBOR_POSTGRES_REPLICATION_USER`, `BASEHARBOR_POSTGRES_INTERNAL_USER`, `BASEHARBOR_OPENBAO_DB_USER` fall back to hardcoded defaults only when the env var is unset/empty.
- file: `internal/runtime/config.go:93-95` — final completeness check treats empty values as fatal: "runtime PostgreSQL configuration is incomplete".
- Consequence: an operator who sets only some of these (e.g. provides a password but omits the replication user) gets a generic "incomplete" error and must discover which key is missing by reading the source. The per-key "X is required" message on line 51 only fires for ports, not for the credential keys.
- Proposed card: add per-key "BASEHARBOR_<KEY> is required" errors mirroring the port path (or build an ordered list of missing keys into one actionable error). Severity: minor (DX / validation-error quality, H-V45 family).

### F2. Docs-vs-code drift: documented-but-absent provider keys

- `docs/spec/service-access.md:30` documents `BASEHARBOR_LOKI_TLS_CERT_FILE` as a *provider-identifier example* ("replace SERVICE with the upper-case provider identifier, for example BASEHARBOR_LOKI_TLS_CERT_FILE"). Not a real code key — it is illustrative. Not drift; verify the example still holds against the generic `BASEHARBOR_SERVICE_TLS_*` family in `internal/serviceaccess/policy.go:12-21`.
- `docs/releases/v0.4.8.md:114` / `docs/de/releases/v0.4.8.md:114` reference `BASEHARBOR_PROVIDER_PROMETHEUS_SHARING_BOUNDARY=<name>` in a release note. Not present in non-test code. Likely a released-then-retired or pattern-level reference.
- `docs/development/v0.4.23-release-requirements.md:61,114` reference `BASEHARBOR_PUBLIC_EVIDENCE_FILE` / `BASEHARBOR_PRIVATE_EVIDENCE_FILE|JSON`. These are release-pipeline env vars, not `baha` runtime keys.
- Proposed card: add a maintenance note (or a generated env-key registry) that flags release/development docs keys that are not resolved by any non-test Go source, so drift is caught. Severity: minor (doc hygiene).

### F3. #1650 leakage class — ambient env reliance in the test suite

The suite sets `BASEHARBOR_*` / XDG / PATH env vars via two mechanisms:
- 2025 of 2064 uses `t.Setenv(...)` (auto-restored per test — safe).
- 39 use raw `os.Setenv` (no auto-restore). Of these, the important ones:
  - `cmd/baha/runtime_integration_test_support_test.go:960` — helper `createRuntimeIntegrationBootstrapTarget` sets `BASEHARBOR_TARGET` and returns it as an `error`; the caller (`TestRuntimeIntegrationBootstrapTargetSelectsAfterCreate`) has already called `t.Setenv("BASEHARBOR_TARGET", target)`, so the process-level set is overwritten by the test's own `t.Setenv`. Not a leak in this path, but the helper's return-value-as-error idiom for `os.Setenv` is fragile and easy to misuse by a caller that does NOT wrap in `t.Setenv` — the ambient value would then leak into subsequent tests.
  - `cmd/baha/shared_core_dedup_runtime_test.go:124,128` — sets `application.ProviderScopeEnv(capability.ProviderPostgreSQL)` without restore; wrapped in a `defer os.Setenv(...previous)` inside an immediately-invoked closure (lines 129-131). Safe, but the restore only runs if the closure body reaches the defer; an early `t.Fatal` before line 129 would leave the ambient value set.
  - `internal/telemetry/otlp_test.go:96` — sets `application.OTLPEndpointEnv` to a bad value; no explicit restore shown — verify whether a preceding `t.Setenv` or `defer` covers it.
  - `internal/stableid/lock_probe_platform_test.go:44` and `internal/cli/terminal_test.go:30` and `providers/runtime/podman/local_authority_verify_test.go:83` set `PATH`/`NO_COLOR` — these are test-local values and low-leakage risk.
- Proposed card: audit every raw `os.Setenv` in a `_test.go` for a paired restore (`t.Setenv`, `defer os.Setenv`, or explicit `os.Unsetenv`); the helper idiom at `runtime_integration_test_support_test.go:960` should switch to `t.Setenv` + `defer` or return a cleanup func. Severity: medium (test isolation / #1650 class — ambient env leaking across parallel or sequential tests can flip behavior).

### F4. Env-var precedence is explicit for Target, implicit/flag-absent for serve

- `cmd/baha/context_terminal.go:204-236` `effectiveContextOrigin` codifies the precedence acceptance criterion: (1) explicit `--target` flag / context override, (2) shell-process env var, (3) configured default / unique configured target. This is a documented, test-checked precedence — good.
- `cmd/baha/serve.go:147-174` `runtimeExecutorConfigFromEnv` / `controlPlaneConfigFromEnv` read **only** from `os.Getenv(...)` (no CLI flag override, no config-file fallback) for the Core runtime executor and control plane. This is intentional (runtime bootstrap is config-file/env driven) but worth noting as an acceptance criterion: there is no flag/env tie-breaker, so an operator cannot override `BASEHARBOR_API_LISTEN_ADDR` via flag. Documented in `docs/spec/control-plane-runtime.md` as env-driven. No bug; recorded as a precedence-surface fact.

### F5. Config validation error quality (H-V45 cross-ref)

This is a good precedent for validation-error quality. Cross-ref H-V45: no duplicate; this is the positive reference the slice should point back to.
