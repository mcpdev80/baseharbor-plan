## Findings

### F1 (LIVE, severity LOW) - org-config `parseConfig` drops unknown/mistyped YAML keys silently

- File: `internal/orgconfig/source.go:286` `parseConfig` => `yaml.Unmarshal(content, &config)` WITHOUT
  `yaml.KnownFields(true)`. The decode then runs `config.Validate()` (source.go:289), which only checks *declared*
  fields. A top-level or nested key that is a typo or unsupported (`unknownThing: ...`, or `default:` instead of
  `defaults:`) is accepted and silently dropped rather than failing closed.
- Repro (temporary in-tree test, since deleted):
  `parseConfig([]byte("apiVersion: baseharbor.organization/v1\norganization: acme\nunknownThing: x\ndefaults:\n  target: local\n"))`
  => `parseConfig` ACCEPTED, `Organization == "acme"`. The same library does reject *duplicate* keys (line-11
  "already defined") and required-field empties (org-name typo fails at `Config.Validate`, target.go:165), so the
  blast radius is optional sections: defaults/targets/providers/trust/policies/team are silently reduced to whatever
  is spelled correctly.
- Consequence: an operator who fat-fingers a key in `organization.yaml` gets a quieter, partially-populated
  configuration than intended (for example an empty `organization` still fails closed, but an omitted `environments`
  block or a mistyped `providers` entry does not) and the tooling never flags the drift - the exact "default drift
  between docs and code" surface the mission names, on the parse side.
- Fix (card acceptance): decode with `yaml.KnownFields(true)` (wrap the decode so the error names
  "unknown field in organization configuration"); regression: a config carrying an unknown top-level key fails at
  `parseConfig` with a non-empty error, asserted in `internal/orgconfig` (extend existing `*_test.go` family).
- Write-set: `internal/orgconfig/source.go` (single call site). Within a bug-hunt card scope.

### F2 (LIVE, severity LOW) - deployment `config.yaml` `decodeConfig` drops unknown/mistyped YAML keys silently

- File: `internal/deployment/target.go:328` `decodeConfig` => `yaml.Unmarshal(data, &cfg)` WITHOUT
  `yaml.KnownFields(true)`. `decodeConfig` validates version (target.go:331) and field content (target.go:340) but
  never rejects an unknown key.
- Repro (temporary in-tree test, since deleted):
  `decodeConfig([]byte("version: 1\ndefaul-target: ghost\naccess:\n  local:\n    provider: docker\n    reference: host\n"))`
  (ConfigVersion == 1) => `cfg.DefaultTarget == ""`: the mistyped `default-target` key was silently DROPPED. The
  version gate still catches a wrong `version`, but a wrong *optional* key is dropped. Same decoder path is used by
  `LoadConfig` (target.go:245) and `LoadConfigForMutation` (`internal/deployment/config_mutation.go:38`).
- Consequence: a mistyped `default-target`, `docker-endpoint`, or nested `prompt` key in `config.yaml` is silently
  ignored and the effective config resolves to a reduced set - a classic default-drift-between-docs-and-code
  manifestation. Docs describe the file as "Target definitions, Access definitions, defaults and prompt preferences"
  (`docs/explanation/targets.md:91`); a typo in any of those four sections is accepted without a diagnostic.
- Fix (card acceptance): decode with `yaml.KnownFields(true)` and return a named error ("unknown field in BaseHarbor
  config"); regression asserting a config carrying an unknown key fails at `decodeConfig`, in `internal/deployment`.
- Write-set: `internal/deployment/target.go` (single decode call site). Within a bug-hunt card scope.

### F3 (VERIFIED-CLEAN / documented, informational) - org-config defaults precedence is fail-closed

- `resolveEffectiveInner` (`internal/orgconfig/effective.go:84-199`) layers defaults `builtin -> organization ->
  environment -> team -> invocation` by `scopeOrder` (`internal/orgconfig/scope.go:25-28`); `applyDefaults`
  (`effective.go:261`) and `recordCandidates` (`scope.go:138`) implement the precedence.
- Undeclared effective target/provider/stack/policy DO fail closed: re-probed
  `ResolveEffective(..., Defaults: {Target:"ghost"})` => `effective target "ghost" is not declared by organization
  configuration` (`effective.go:152`). Confirmed at tip.
- `effective.go` resolves provider references against `state.Config.Providers` (`:168-175`) and rejects an undeclared
  provider. So the defaults-vs-validation gap is NOT present in the resolution layer - it is isolated to the two YAML
  decode call sites in F1/F2. This is noted so a future card does not re-hunt the precedence layer.

### F4 (informational, not a defect) - repository `.env` / `COMPOSE_ENV_FILES` precedence is explicit

- `configureRepositoryComposeEnvironment` (`cmd/baha/app_context.go:691`) short-circuits when
  `COMPOSE_ENV_FILES` is already set (external precedence), then collects
  `<state-root>/init.env` (`app_runtime_init.go:459`, name `init.env`) BEFORE `<repoRoot>/.env`
  (`app_context.go:696-697`) and joins them in that order into `COMPOSE_ENV_FILES`.
- No `.env` file precedence edge found: the state-root `init.env` is checked first (isolated state wins over the repo
  file), and an already-set `COMPOSE_ENV_FILES` always wins. This is the documented, non-default-drift path.
  Informational only - no card.
