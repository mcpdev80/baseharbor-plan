### Remote `app up` architecture fully traced
`baha app up` for a connector-bound Target runs through `cmd/baha/app_remote_lifecycle.go`
→ `remoteApplicationTransport` → `targetsession` mTLS transport over the connector.
The required chain:
1. `baha node add <node> --runtime podman --tenant-id UUID --core-url https://127.0.0.1:18201
   --core-address 127.0.0.1:18202 --ca-file core-server.pem`
   → creates target definition + one-use enrollment bundle via the operator API
   `/api/v1/connectors/enroll` (requires a verified operator principal + tenant scope).
2. `baha node connect <bundle> --connector-bin <bin>`
   → installs a systemd user unit that runs `baseharbor-node-connector`
   (built successfully from `baseharbor-node-connector/cmd/baseharbor-node-connector`),
   which does the mTLS handshake at `/api/v1/connectors/enroll` and enrolls the node.
3. `baha app up` → CLI dials the connector, mTLS handshake with SPIFFE server identity,
   dispatches apply through `targetsession.Session.Dispatch`.

## Blocker (documented, not worked around)

### Blocker A — operator session is browser-interactive OIDC
`requestNodeAuthorization` (cmd/baha/node.go) calls `operatorauth.LoadSession`,
which requires a persisted OIDC `id_token` with a valid signature/issuer/audience.
The `dev` environment is "trusted-local" for the *machine-authorization* path
(internal/operatorauth/authorization.go:231 — `!ManagedEnvironment(env) && !ok`
→ `trusted-local` allowed), but the **operator API HTTP middleware**
(internal/httpsecurity/middleware.go `Protect`) always requires a valid bearer token.
`baha login` (internal/operatorauth/login.go) performs Authorization Code + PKCE
with a local callback + browser redirect; the `bh-operators-dev` realm +
`baseharbor-cli-dev` client are created on first real login
(identityprovider.EnsureManagedOperatorOIDC). This cannot complete headless in the
VM session. Confirmed: `node add` returns
`node enrollment requires a valid Core operator session`.

### Blocker B — operator tenant/membership not seeded in Core
The operator API `ResolveTenant` (internal/database/identity_tenant_resolver.go)
requires exactly one tenant + roles row in the `baseharbor` DB
(`tenants`, `memberships`, `external_identities`). All three tables are EMPTY after
Core bootstrap (verified via `r27-count`): the Core `--control-plane-only` bootstrap
provisions OpenBao/postgres/Keycloak/Core Identity only; the operator membership seed
is not part of control-plane bootstrap and is not created by any runtime path reached
so far. Without a seeded operator tenant + an authenticated principal, the operator
API cannot resolve a tenant scope for `node add`'s authorize call.

### Blocker C — CI Targeted HA jobs unreachable from a PR (FINDING, Owner scope)
`.github/workflows/ci.yml`:
- `targeted_ha_docker` / `targeted_ha_podman` fire only on
  `github.event_name == 'push' && startsWith(github.ref_name, 'runtime-validation/ha/')`
  (ci.yml lines 176 and 218).
- The PR planner step hardcodes `runtime_required=false` (ci.yml line ~527), so the
  `pr_selected_runtime` matrix never requests a runtime job on a PR, and the HA jobs'
  `needs.pr_plan.outputs.runtime_required == 'true'` gate (ci.yml lines 584/640/683)
  is never satisfied from a PR.
Consequence: a new connector-acceptance test cell placed in any existing group is
either SKIPPED by the path rule or never scheduled on the PR. Making the cell run on
PR requires either (a) a new CI group/trigger that runs on PR push (Owner scope:
`.github/**` is Owner-owned — report, do not edit), or (b) pushing a
`runtime-validation/ha/<group>/<runtime>/` branch (not a PR). This is reported as a
finding with file:line per mission requirement; the change itself is Owner scope.
