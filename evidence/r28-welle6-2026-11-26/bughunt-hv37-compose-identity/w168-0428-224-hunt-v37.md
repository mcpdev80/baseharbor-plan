## Findings (per row: file:line + finding + proposed card line)

### Finding H-V37-A: `RuntimeAuthorizedServices` dedups by name but does NOT validate uniqueness of a service across runtime permissions

- file:line: `internal/application/runtime_identity_workload.go:57-72` (`RuntimeAuthorizedServices`); dedup confirmed via `seen` map + `sort.Strings` at line 70.
- file:line: `internal/application/manifest_validation.go:189-240` (`validateRuntimePermissions`). Each permission's own `seenServices` rejects a duplicate *within* one permission (line 218-220), and each permission's `Capability` must be unique (line 205-208). But a single service name (e.g. `api`) may be named in two different runtime permissions (two capabilities), and that cross-permission duplicate is not rejected.
- file:line: `internal/application/manifest.go:38-48` (`RuntimePermission` struct) — no cross-permission uniqueness guard.
- Consequence: deterministic ordering (sorted) and id stability (sha256 per name) still hold because `RuntimeAuthorizedServices` dedups. But the manifest can authorize the same service under two capabilities; the broker (`internal/runtimebroker/broker.go:287` -> `ensureRuntimeServiceTokensFile`) and the workload plan (`cmd/baha/app_workload.go:335`) both iterate `RuntimeAuthorizedServices`, so the duplicate is collapsed to one identity file and one token secret. Behavior is consistent (no crash, no ordering change), but the intent "service identity is one-to-one with an authorized component" is silently loose.
- Risk: LOW. Ordering and id stability are intact; the only gap is a missing manifest-level uniqueness assertion.
- Proposed card line: card 0428-xxx "reject a runtime permission that names a service already authorized by another runtime permission" at `validateRuntimePermissions`; add a second `seenServices` set shared across all permissions (or a top-level `seenServices` keyed by service) and return an error on cross-permission duplicate. Test: extend `TestRuntimeIdentityWorkloadOverrideUsesServiceScopedTokenForExplicitPermission` with a second permission naming the same service and assert parse-time rejection.

### Finding H-V37-B: compose binding discovery dedups service set via map but does not dedup a service that is declared twice in the same compose file (unlikely; docker compose itself rejects) — ordering still safe

- file:line: `cmd/baha/app_workload.go:338-356` (`repositoryWorkloadBindingPlan`) — `config.Services` is parsed from `compose.ConfigJSONProjectFilesEnv` as `map[string]...` (struct field `renderedComposeConfig.Services map[string]...` at line 311-314), so a service declared twice in source is already deduped by JSON decode. `plan.RuntimeIdentityServices` is sorted at line 356.
- file:line: `cmd/baha/app_workload.go:329-332` (`selected` map) — dedups the workload component selection.
- Consequence: no loose duplicate path; ordering deterministic; id stable. This confirms H-V37-B is clean — no card needed. Documented as a null finding.

### Finding H-V37-C: id stability across apply/reconcile is correct — token is read-through, not regenerated

- file:line: `internal/application/runtime_identity.go:132-169` (`EnsureRuntimeServiceIdentities`) — for an existing token file the value is read (line 147) and reused (line 154/166); only a missing token is generated (line 159). Stable across re-renders.
- file:line: `internal/application/runtime_identity.go:84-96` (`RotateRuntimeIdentity`) — rotation explicitly re-generates each service token (line 88) and clears revocation (line 97); this is the intended id-change path.
- file:line: `cmd/baha/app_workload.go` reconcile path calls `MaterializeRuntimeIdentityWorkloadOverride` -> `EnsureRuntimeServiceIdentities` (line 227), re-reading stable tokens.
- file:line: `internal/runtimebroker/broker.go:287` reconcile also calls `EnsureRuntimeServiceIdentities`, so broker token files converge to the same identity.
- Consequence: id stability holds; the only id mutation is the explicit rotation path. Clean. Documented as a null finding.

### Finding H-V37-D (POSITIVE, worth a regression test): the "legacy fallback" for a service consuming runtime identity but NOT named in any permission silently drops service-scoping

- file:line: `internal/application/runtime_identity_workload.go:248-263` — for each `runtimeServices` service, `serviceIdentities[service]` is looked up; if the service is NOT in the sorted `RuntimeAuthorizedServices` set (i.e. `!explicitlyAuthorized`), it falls back to the shared legacy app token `baseharbor-runtime-token` (line 252-263) instead of a service-scoped token.
- file:line: `internal/application/runtime_identity_workload.go:335` (`repositoryWorkloadBindingPlan`) only populates `plan.RuntimeIdentityServices` for services that are `explicitlyAuthorized` OR carry a legacy `BASEHARBOR_RUNTIME_TOKEN_FILE` env var (line 342-346). So a workload service that reaches the broker at runtime but is not in a runtime permission gets the shared legacy token.
- Consequence: ordering and stability are fine, but a service consuming the broker without an explicit runtime permission reuses the *application-wide* token rather than a per-service token. That weakens the "one identity per authorized service" property the manifest validation implies. The legacy env-var gate (`BASEHARBOR_RUNTIME_TOKEN_FILE`) is a backwards-compat escape hatch, so this is not a crash — but it is the one place service-scoped identity is silently downgraded.
- Risk: MEDIUM (security posture: fewer distinct tokens than the manifest implies). This is the strongest candidate for a card.
- Proposed card line: card 0428-xxx "document or tighten the runtime-identity service scoping fallback" — either (a) reject a workload service that reaches the runtime broker without an explicit runtime permission (fail closed), or (b) add a doc/contract assertion + regression test in `TestRuntimeIdentityWorkloadOverrideUsesServiceScopedTokenForExplicitPermission` asserting the fallback only when the legacy env var is present and never otherwise. Test route: `internal/application` package tests already cover this path (existing `MaterializeRuntimeIdentityWorkloadOverride` tests); wire via the standard `go test` CI group covering `internal/application`.
