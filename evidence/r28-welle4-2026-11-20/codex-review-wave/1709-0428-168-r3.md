## P1 — Legacy source survives same-ID/provider replacement, with one unresolved owner-map case

The migration is wired into the actual Keycloak registration path. `internal/identityprovider/keycloak_realization.go:163-205` creates `LegacyReconciliation` and passes it to `RegisterProviderSignals`; `internal/observability/registry.go:257-275` calls `RebookLegacySignals` inside the same `mutate` callback before the `(ID, provider)` replacement loop. A foreign owner's derived ID is disjoint from the registering application's ID, so that later replacement cannot remove it. The focused same-mutation test is `TestRegisterProviderSignalsRebooksLegacyBeforeReplacement` (`internal/observability/keycloak_legacy_migration_test.go:294-356`); the production-path integration `TestRegisterKeycloakSignalsPreservesLegacySourceForOwner` exercises a different owner and both enabled/disabled caller metrics (`internal/identityprovider/keycloak_legacy_migration_integration_test.go:22-145`). Mutation proof C in `evidence/r28-welle4-2026-11-20/keycloak-signal-migration/round-3.md:170-178` records these tests failing when derived rebooking is removed.

However, the new owner-scan correction does not cover a missing owner directory when the scan finds other owners. `ownerProjectMaps` returns immediately on any non-empty `recorded` map (`internal/identityprovider/keycloak_realization.go:235-245`); it calls `legacyLiteralOwners` only when the entire map is empty (`:242-244`). A legacy source whose `OwnerApplication` is absent from that non-empty map then reaches `LegacyReconciliation.ProjectFor`, which falls back to the replacing deployment's project (`internal/observability/migration.go:327-345`, especially `:344`). `CanonicalApplicationProject` cannot make that caller project carry a different owner anchor, so the moved record fails the application-owner environment derivation and remains unlistable (`internal/observability/environment.go:170-180`). This is the exact mixed state of a pre-scoping owner with no retained state directory while a newer registering/other app does have a state directory. The existing integration fixture writes appA's state directory (`keycloak_legacy_migration_integration_test.go:41-42,151-164`), so it does not exercise that case.

**Blocking recipe:** in `internal/identityprovider/keycloak_realization.go:235-245`, merge the derived legacy-owner map into the recorded-owner map for owners that have no state-directory entry; do not make this recovery conditional on the entire recorded map being empty. If any legacy source owner still cannot be resolved, return an error before `RegisterProviderSignals` mutates the registry rather than letting `ProjectFor` substitute the caller project. Propagate `ListAll` failure from `legacyLiteralOwners` rather than converting it to an empty owner map. Add an integration regression with a legacy appA source and no appA state directory, plus a valid appB state directory; run appB's real `registerKeycloakSignals` path and assert appA's source is rebooked under appA's identity, visible to appA, and removable.
