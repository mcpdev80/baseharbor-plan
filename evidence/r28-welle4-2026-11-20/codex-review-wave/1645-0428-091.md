## P1 — Perses plugin and actual runtime path

The candidate builds a native `TempoDatasource` resource and pins a Perses contract witness: `internal/metrics/perses_tempo_datasource_test.go:141-188` checks the emitted resource against that witness; `internal/metrics/perses_tempo_contract.go:17-41` describes the upstream model/sample provenance. The health verifier also issues a TraceQL query with a deadline (`internal/metrics/perses_tempo_datasource.go:594-631`). This is meaningful contract and mock-server evidence, but it does not prove that the pinned Perses runtime loads the datasource plugin and reaches the real Tempo service-access endpoint.

The runtime endpoint is host-loopback: `internal/traces/tempo.go:511-523` returns `https://127.0.0.1:<BASEHARBOR_TEMPO_PORT>`. The candidate rewrites that to `localhost` without changing the port (`internal/metrics/perses_tempo_datasource.go:517-535`). Perses is configured to run in the management gateway's network namespace, with its own loopback listener (`internal/application/perses_runtime.go:127-133`); the host-published Tempo access port is not thereby made a listener on that namespace's loopback. The candidate test asserts the rewritten URL using a Go-side HTTP fixture (`internal/metrics/perses_tempo_datasource_test.go:141-188`), not a Perses container. Its own fixture comment at `perses_tempo_datasource_test.go:730-738` also describes a synthetic gateway and environment-dependent client identity.

**Required recipe:** in `internal/metrics/perses_tempo_datasource.go`, produce a datasource endpoint routable from Perses' actual network namespace through the managed Tempo access boundary; do not substitute `localhost` for the host-published loopback endpoint. Add a CI-routed native integration test using the pinned Perses image and a managed Tempo access gateway; assert the datasource plugin loads and an authorized TraceQL query reaches Tempo. Stop if the pinned plugin cannot use a supported routable service-access endpoint or if the test cannot prove the real path. This blocks acceptance under the card's “selected authorized Tempo datasource” and verified-path requirements.

## P2 — Authorization and fail-closed mTLS

`tempoProviderHTTPClient` resolves the environment policy (`internal/metrics/perses_tempo_datasource.go:467-470`), then copies it and forcibly disables `AuthenticationRequired` before reading existing TLS material (`:482-489`). `internal/serviceaccess/pki.go:103-124` uses that flag to decide whether to load client credentials; with it false, the client certificate/key are blanked (`:120-123`). The candidate only marks the client authenticated if a certificate was already returned (`perses_tempo_datasource.go:491-498`). Thus an environment whose service-access policy requires mTLS can proceed without presenting the required identity. Candidate fixtures use `application.New(..., "dev", ...)` (`perses_tempo_datasource_test.go:45-56`), so the tests do not exercise the strict policy case. This violates the card's fail-closed authorization requirement.

**Required recipe:** in `internal/metrics/perses_tempo_datasource.go:482-496`, preserve the resolved `AuthenticationRequired` policy when loading/constructing the client and return `TempoAuthorizationError` if the required enrolled client identity is absent; do not downgrade policy to make provider server-only PKI usable. Add tests for strict stage/production policy with missing credentials (must fail closed), with authorized credentials (must present mTLS), and for dev only where policy permits it. Stop if a policy-required request can be built without a client certificate or if an unauthorized/missing identity can reach the query.
