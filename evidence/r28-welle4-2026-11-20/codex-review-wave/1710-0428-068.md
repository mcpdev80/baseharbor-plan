## Acceptance review

### Terminal-only context and shell hook — NOT MET (blocker)

The implementation emits a snippet but does not cause the current shell to evaluate it. `runContextUse` only writes the comment and `activationSnippet` to its child process's stdout (`cmd/baha/context_terminal.go:120-150`). The generated hook does not call `context use` or evaluate that output; it invokes `baha context show` and copies the already-effective value into the child shell (`cmd/baha/completion_setup.go:41-70`). Sourcing this completion output and then running `baha context use TARGET` therefore prints an export statement but does not change the parent shell's `BASEHARBOR_TARGET`. The next prompt hook reads that unchanged environment/default and cannot infer the target supplied to the prior command.

`context clear` has the same process-boundary defect: it calls `os.Unsetenv` in the `baha` child process (`context_terminal.go:153-163`), which cannot unset the interactive parent shell. Its test calls `runContextClear` directly in the Go test process and checks that process's environment (`context_terminal_test.go:121-133`); that is not the actual CLI or shell path.

**Required recipe:** implement the owner-approved sourceable-snippet + one-time hook so the shell evaluates the exact `context use`/`clear` result in its own process; keep selection terminal-local and do not add a marker file. Add an end-to-end test that sources the generated setup in an actual shell, runs `baha context use TARGET`, observes that target from a subsequent command in the same shell, then runs `baha context clear` and observes the variable unset. Run two independent shells and prove their targets remain different. Stop if `use` merely prints text, if `clear` only changes the child process, or if one shell inherits another shell's selection.

### Bash/Zsh/Fish hook behavior and completion safety — NOT MET (blocker)

`activationPrefix` uses the same Bash-style `PROMPT_COMMAND` string for both Bash and Zsh (`cmd/baha/completion_setup.go:53-70`); there is no Zsh `precmd` registration. The Fish branch defines `_baha_context_hook` but ends with `functions -a fish_prompt;` (`:43-52`), which does not register or invoke that function as a Fish prompt hook. The generated hook test checks only that the text `_baha_context_hook` appears in the output (`cmd/baha/context_terminal_test.go:137-148`), not that each shell executes it. `completionHookInstalled` is defined but unused (`completion_setup.go:74-79`), so no idempotent installation guard is wired into the generated completion scripts.

**Required recipe:** in `cmd/baha/completion_setup.go` and the shell-specific emitters in `cmd/baha/completion.go:203-270`, use the native prompt mechanism for each supported shell, preserve any existing prompt/completion handlers, and make repeated completion setup idempotent. Add real-shell tests for every shell the product claims to support, including sourcing the script twice and checking existing completion still works; verify noninteractive `bash -c` and pipelines are not given interactive behavior. Stop if a supported shell does not actually invoke the hook or existing completion/prompt behavior changes.

### Precedence and semantic fallback — PARTIAL (blocker)

`effectiveContextOrigin` implements only explicit context override → `BASEHARBOR_TARGET` → configured default/unique configured target (`cmd/baha/context_terminal.go:187-213`). It does not distinguish the owner-required command-scoped environment stage from the terminal-owned `BASEHARBOR_TARGET` stage, and its tests set the process environment directly rather than invoking a command with an inline environment assignment. It also omits the existing activated user target and organization preference resolution: the established selector `selectedTargetName` checks explicit → environment → persisted target → configured default/unique target (`cmd/baha/target_selection.go:59-83`), and `effectiveTarget` then applies organization preferences (`cmd/baha/target.go:88-124`).

That omission affects behavior, not just the label in `context show`: after the generated prompt hook runs, its `context show` can return a configured default and export it as `BASEHARBOR_TARGET`, causing normal commands to prefer that environment value over an already activated user target. This conflicts with the brief's fallback requirement and semantic parity while leaving the persisted target file itself untouched.

The purported precedence tests call `effectiveContextOrigin` directly (`context_terminal_test.go:70-105`); they do not execute a real CLI command or a shell hook. The tests cover explicit context, one process environment, and configured default, but not all four ordered stages. Round-1 evidence `cli2-context-shell/round-1.md` describes the tests as one per precedence level; that overstates the source tests.

**Required recipe:** in `cmd/baha/context_terminal.go:187-213`, resolve fallback through the existing user/system selection contract without writing or repurposing persisted selection. Keep command-scoped env above terminal env and both above user/system defaults. Add CLI-level tests with a terminal value and a separate inline command environment, explicit flag, and user/system fallback; drive the real command path, not only the helper. Add mutation proofs per precedence stage: removing/reversing each stage must fail its corresponding command-path regression. Stop if explicit flag, command environment, terminal environment, and user/system default cannot each be observed as the winner in the required order or if installing the hook changes an already activated user target.
