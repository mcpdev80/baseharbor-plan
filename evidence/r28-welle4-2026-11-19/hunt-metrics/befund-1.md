## Befund 1 (medium): the application-class metrics registration is visibility-only — the registry entry is not load-bearing for the scrape chain

- Files: `internal/metrics/realization.go:166-186` (RegisterTarget), `internal/metrics/prometheus_files.go:47-83` (syncProviderTargets), `internal/metrics/prometheus.go:345-348` (Driver.Verify query), `internal/observability/registry.go:588-612` (ListApplicationMetrics).
- #1677 made class `application` visible (the registry switch at `registry.go:509-512` plus the explicit `ListApplicationMetrics`). Verified true: an application-class metrics source is now written into `observability/signals.json` on `Bind`, and `ListApplicationMetrics` returns it.
- But the visibility is confined to the verify path. `observability.ListMetrics` keeps `includeApplicationSources=false` (`registry.go:616`), and that is the listing every renderer and inventory consumer calls (`prometheus_files.go:240`, `prometheus_files.go:451`, `runtime_retirement.go:56`). The scrape target itself comes from `targetFileNameFor(...)` written directly by `RegisterTarget` (`realization.go:167`) — a separate, file-only route.

The verify query rebuilds `baseharbor_application`/`baseharbor_environment`/`baseharbor_source` from the manifest (`prometheus.go:346`, `prometheus_verify.go:178`). A stale or wrong endpoint in the registry entry therefore stays permanently invisible: verification still passes as long as the manifest-derived file_sd target is up.
- Witness: `scripts/zz_hunt918_h_test.go` (provider listing sees 0 app-class sources; no `provider--*.json` written) and `scripts/zz_hunt918_i_test.go` (`TestHunt919AppClassVisibilityIsVerifyOnly`: the registered source's Target/Network/Path appear nowhere in the query the chain actually issues). Both PASS at `97a840e54`.
- Severity rationale: medium. Not a user-visible break, but it is a silent-success surface: the new registry entry creates the impression of a second, reconciled source of truth while every consumer of that truth still recomputes from the manifest.

- Files: `internal/observability/registry.go:488-548` (`List` — no environment parameter, no environment field), `registry.go:588-612` (`ListApplicationMetrics`), `internal/metrics/prometheus_verify.go:141-175` (the only environment-aware site), `registry.go:563-586` (`PruneApplicationMetrics` — IS environment-aware).

- The asymmetry is already visible inside the chain: pruning IS environment-scoped (`PruneApplicationMetrics`, keyed on `application:metrics:<app>:<env>:`) while listing IS NOT. So an environment-scoped delete and an environment-blind read coexist on the same ID space.

## Befund 3 (high): no production code ever writes an application-class LOG source — the class-`application` log path is dead, and #1680's reclaim is unconditional

- Files: `internal/observability/registry.go:551-553` (`ListLogs` hardwires `includeApplicationSources=false`), `internal/logs/realization.go:165-178` (RegisterSource), `internal/logs/driver.go:117-130`, `internal/application/runtime_observability.go:83-92` (#1680 reclaim), `docs/architecture/runtime-log-source-contract.md:21-26`.
- The architecture contract names three normalized log source classes including `application`. In code, that class is unreachable:
  - The Loki application registration writes only `Registration` state (a syslog port allocation), never a registry `SignalSource` (`realization.go:176` → `applicationRegistration()`); the class check at `realization.go:173` only rejects foreign classes.
  - `RegisterProviderSignals`/`ReconcileSignals` are the only registry writers for provider identities, and both stamp `registration.Class` (`registry.go:225`), which callers set to `application-provider` or `platform-provider` only (`logs/realization.go:211-214`, `application/runtime_component_observability.go:123-131`).
  - So `ListLogs(…, false, …)` (`registration.go:27`, `overrides.go:105`, `cmd/baha/app_logs.go:140`) excludes a class that is never present. The switch is correct but currently untestable against real product state.
- Corollary for #1680: the reclaim `PruneProviderSignals(id, prometheus, SignalLogs)` at `runtime_observability.go:87-89` runs before any policy decision and on every reconcile. Since Prometheus never legitimately owns a log signal, that call deletes by ID+provider whatever else shares the identity `prometheus:<project>`. #1680 also moved the `id` computation above the policy early-return (`runtime_observability.go:83` vs the previous position), so the reclaim now fires on the metrics-disabled path too — intended, but it means one identity string is a cross-signal delete key.
- Witness: `scripts/zz_hunt918_e_test.go` (PASS) — an application-class log source persists in the registry while every `ListLogs` caller is hardwired to exclude it; `scripts/zz_hunt918_l_test.go` (PASS) — `observability.Remove(id)` and the ID+provider prune are ID-scoped, not class/kind-scoped, and `UpdateSignal` keys on ID+Kind only, so a second class under the same ID and kind silently overwrites the first (observed: the surviving log signal was `class=application-provider`, the `application` entry was gone without error).
- Witness (same shape at the reconcile boundary): `scripts/zz_hunt918_m_test.go` (PASS) — two owners of one shared collector identity (`loki:bh-shared`) reconcile the same ID+provider; `ReconcileProviderSignals` is last-writer-wins on Class/Scope/OwnerApplication (owner A's `platform-provider`/`shared` entry is replaced by owner B's `application-provider`/`application` entry, silently), and owner A's reclaim (`PruneProviderSignals(id, provider, kinds)`, the exact call #1680 introduced) then deletes owner B's registration. The identity carries no owner dimension, so "reclaim my signals" is really "reclaim whoever's signals are under this ID right now". The existing `TestReconcileProviderSignalsEmptyDesiredPrunesOnlyOwnedProvider` (`registry_test.go:120`) proves the provider dimension is guarded — the owner/class dimensions are not.
- MCP/HTTP part of the mission question: `baha app logs` / `baha logs` are `compose logs` passthroughs (`cmd/baha/app_access.go:139-168`) and are explicitly `excluded` from machine coverage (`docs/reference/cli-machine-coverage.md:33,92`). The `false` therefore applies to CLI, MCP and HTTP alike — but the reason is that all three ignore the log-class dimension entirely, not that an exclusion was propagated.
- Severity rationale: high. Two independent silent-success shapes: a documented source class with no writer, and an overwrite-prone ID+Kind key that loses entries without an error.
- Existing cards: `0428-101` (ID-Raum, blocked) is the nearest; it does not cover the missing class-`application` log writer. Recommend one new card per shape.

## Befund 6 (medium): a metrics source with `verification: none` produces neither a scrape target nor an assertion — deploy and verify both go green over it

- Files: `internal/metrics/prometheus_files.go:66-68` (`if source.Verification == ObservabilityVerifyNone { continue }` inside `syncProviderTargets`), `internal/metrics/prometheus_verify.go:184-186` (same skip in the verify loop), `internal/metrics/prometheus_files.go:159-178` (`providerMetricNetworks` applies the identical skip).
- This is deliberate for the workload-only snapshot identity — `runtime_observability.go:96-112` registers the symbolic `prometheus:<project>` metrics source with `Verification: none` precisely so it never becomes a scrape target, and #1677's own test names that case ("skips only snapshot metadata"). But the same rule is the only gate on the provider path: a provider whose metrics signal is `requires_adapter` (status not collectable) or a registration that reaches `verification: none` yields a source that `ListMetrics` returns, then every downstream stage drops. The chain is: registry non-empty, file_sd empty, verify asserts nothing, `verifyProviderSourcesAt` returns `nil` when its inputs are empty (`prometheus_verify.go:154-156`).
- Witness: `scripts/zz_hunt918_k_test.go` (PASS) — one `verification=none` provider-class source: `ListMetrics` returns 1, `syncProviderTargets` writes 0 files, and the verify loop logs "verify path skips source postgres:shared". That is a genuine silent success: the operator sees a green metrics verification with zero series collected.
- Same shape on the destroy/prune side, in the opposite direction: `pruneApplicationTargetsFromFiles` (`internal/metrics/prometheus.go:418-442`) deletes every target FILE whose name is not in `desired`, but derives the registry `keep` set from `m.Metrics.Sources` intersected with `desired`. A registry entry whose file is already gone (hand-deleted, or written by a release whose file naming differed) is therefore kept forever while its file is not recreated — the prune converges on the intersection rather than on `desired`. `scripts/zz_hunt918_j_test.go` (PASS) confirms the normal path converges (1 entry survives, the stale one is pruned), so this is a boundary note on the recovery case, not a live break.
- Cross-check against card `0428-103` ("postgres-/valkey-Adapter ohne Plan", planned): the adapter-required signal status is what routes a provider into this shape (`capability/integration_contract_test.go:198-206` proves `requires_adapter` is not collectable), so the moment an adapter is registered without flipping verification to a real mode, the metrics capability reports success over nothing.
- Severity rationale: medium. The individual skips are each correct; the composition has no counter-assertion that "at least one source produced at least one scrape target", and `docs/DEVELOPMENT_GUIDELINES.md` §2 ("fail closed") and §8 ("do not report success before required verification succeeds") both argue for one.
- Recommend a card: add an explicit "metrics enabled but zero scrape targets realized" outcome (fail or degrade) rather than a nil return.

## Befund 7 (medium): the runtime-metrics target file key omits the environment while the stored group labels it — two environments of one application collide on one file

- Files: `internal/metrics/runtime_source.go:202-207` (`runtimeTargetFileName` = `sha256(application, callerService, resourceName)`, no environment), `internal/metrics/runtime_source.go:134-146` (the group it writes DOES carry `baseharbor_environment: e.environment`), `internal/metrics/runtime_source.go:185-192` (the read-time ownership check DOES compare `baseharbor_environment`).
- Consequence: for one `(application, callerService, resourceName)` tuple in two environments, the shared runtime-metrics directory (the broker volume mounted at `/var/lib/baseharbor/runtime-metrics`, `internal/runtimebroker/compose_render.go:202,243,312`) holds exactly one file. The last writer wins on the label; the loser's `readTarget` then fails with `runtime metrics target ownership mismatch` and, per `Execute`, that is a hard error (`internal/metrics/runtime_source.go:60`), not a re-register. `runtime.create` is likewise an unconditional overwrite, so an existing source is silently retargeted to the other environment's label.
- The scrape side amplifies it: the file is consumed under `job_name: baseharbor-applications` (`prometheus_render.go:195-205`, globbing `/etc/prometheus/runtime-targets/%d/*.json`), and each registration's `RuntimeVolume` is per-application+environment (`application.MetricsRuntimeTargetVolumeNameForNamespace`). One volume per environment means one file per volume, so the collision is only reachable where two environments share a volume — i.e. through the broker's single global targets dir, not the per-deployment volumes. The reachable shape is therefore the broker path, and the failure mode is a mismatch error, not a wrong scrape.
- Witness: `scripts/zz_hunt918_o_test.go` (PASS) — one tuple, `dev` then `prod`: identical file name (`runtime-63f7f115…json`, 1 entry for both writes), both `readTarget` calls succeed immediately after their own write, and a `dev` executor reading after the `prod` write fails with `runtime metrics target ownership mismatch`.
- Severity rationale: medium. Fail-closed at the read boundary (no wrong-environment scrape), but `runtime.get`/`runtime.create` for one deployment can be broken by an unrelated deployment's later write, and nothing in the file key or the error names the other environment.
- Recommend a card: bind the environment into `runtimeTargetFileName` (matching what `readTarget` already asserts).
