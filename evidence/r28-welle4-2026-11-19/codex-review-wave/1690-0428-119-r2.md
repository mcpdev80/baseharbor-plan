## Findings

### 1. Blocking — `sameProviderInstanceAuthority` omits authority-bearing fields

`internal/application/provider_consent_authority.go:500-510` compares ID, provider identity/version/protocol, kind/capabilities, scope, sharing boundary, ownership, and `OwnerApplicationID`, but omits `ProviderInstance.OwnerEnvironment` and `Reference` (and the registry's `OwnerApplication` field).

`Reference` is used to resolve external-scoped providers: `internal/capability/registry.go:127-151` matches `placement.ExternalReference` against `instance.Reference`. A change from one external registration reference to another can therefore preserve the instance ID/count and compare equivalent here while selecting a different registration. `OwnerEnvironment` constrains binding at `registry.go:225-230` and registry validation at `registry.go:434-439`; changing it can change which environment may bind the instance. The comparator's comment at `provider_consent_authority.go:448-453` says every registry-carried authority field is compared, but these fields are missing. `OwnerApplication` is also omitted; if it is intentionally display-only, record that contract, otherwise include it in equality.

There is a second false-equivalence case in `equalProviderCapabilities` at `provider_consent_authority.go:552-565`: it checks raw slice lengths and then only membership of each left value in the right set. Equal-length slices such as `[sql, sql]` and `[sql, secrets]` compare equal, despite the latter supporting an additional capability. `capability.Registry.Validate` rejects duplicate instance IDs and duplicate bindings, but `validateProviderInstance` (`internal/capability/registry.go:545-589`) does not reject duplicate capabilities.

**Recipe:** Update `sameProviderInstanceAuthority` in `internal/application/provider_consent_authority.go:495-510` to compare the external `Reference` and `OwnerEnvironment` as well as all other consent-authority fields; explicitly document whether `OwnerApplication` participates. Make `equalProviderCapabilities` compare unique capability sets without allowing duplicate slice entries to mask a missing/different capability, or reject duplicate capabilities at the authoritative registry validation boundary.

**Test requirement:** Add same-ID/same-count negative cases changing only `Reference` and `OwnerEnvironment`; add a capability case where duplicate entries currently mask a different capability. Keep the positive different-order test and add reversed binding order coverage. Each negative case must assert `ConsentAuthority.Equivalent` is false.

**Stop criterion:** Stop if any change to external provider reference, binding environment constraint, or effective supported-capability set still compares equivalent; also stop if the documented comparison contract claims all fields while omitting one without a recorded reason.

Do not rely on checking emitted text alone.
