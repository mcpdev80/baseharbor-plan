## B1 — application/provider filename disjointness

I inspected the candidate source, not its comments alone:

- `providerTargetFileName` at `prometheus_files.go:39-44` emits `provider--<hash>.json` or `provider-secure--<hash>.json`.
- `appTargetFileName` at `:59-69` always prepends the constant `application--` to `targetFileName(...)`. Neither application slug `provider` nor `provider-secure` can change that leading prefix.
- `prometheus_render.go:198-199` selects `application--*--*--*.json` and the existing `*--*--*.json` in the applications job. The provider job at `:222-226` selects `provider--*.json`; secure provider jobs select exact `provider-secure--<hash>.json` names at `:233-249`.
- `syncProviderTargets` only treats names beginning with `application--` in its application branch (`prometheus_files.go:124-130`); the provider deletion branch checks only the two provider prefixes (`:131-136`).

Therefore no application target produced by this function, including either example slug, is selected by the provider job or removed by the provider-prefixed deletion branch. **B1 implementation passes.**

The regression `TestRegVisibilityApplicationNamedProviderIsDisjoint` uses slug `provider` and verifies the output prefix and provider-prefix classification. It does **not** call `prometheusConfig` or exercise which emitted globs select the file. The prior review's acceptance recipe required exercising the emitted Prometheus patterns, not only prefix classification. The implementation is disjoint by inspection, but that explicit regression requirement remains unfulfilled. Add focused assertions against the rendered application and provider job file patterns for `provider` and `provider-secure`.

## B2 — application reconciliation and foreign targets

The application namespace reconciliation at `prometheus_files.go:113-130` builds `appKeep` from application target names and removes stale `application--*.json` entries. This correctly removes the stage application target when a later sync selects only dev. Runtime targets are read from a separate path in rendered config (`prometheus_render.go:201-205`); the B2 test also places a runtime-target JSON file in the target directory and compares its digest after sync.

However, the same `syncProviderTargets` loop handles provider-prefixed JSON files at `prometheus_files.go:131-135`. It calls `providerSourcePresent`; that helper at `:166-175` returns false for a provider-prefixed file unless it corresponds to a currently selected non-application source. With an application-only source list, an existing `provider--foreign.json` or `provider-secure--foreign.json` is therefore removed. This contradicts the stated B2 acceptance that foreign provider-prefixed files remain untouched during application reconciliation.

The regression test does not cover this case: it seeds `0-runtime-target.json` and `provider-ca.pem` (`regvisibility_regression_test.go:135-150`), not either provider-prefixed JSON family. Its successful run cannot establish byte preservation for those files. The current test description in `fix-3.md` says foreign provider files survive, while the implementation removes unselected files in those exact prefixes.

**Blocking correction recipe:** make ownership of provider-prefixed files explicit so application-target reconciliation cannot delete foreign provider JSON; preserve stale-provider cleanup only for files the current sync can prove it owns. Extend the stage-then-dev regression to seed `provider--foreign.json` and `provider-secure--foreign.json`, save their byte digests, and assert both survive unchanged alongside the runtime-target file. Stop acceptance if either is removed or rewritten.
