## B2 — provider ownership versus deselected sources — REQUEST CHANGES

The guards exist in `internal/metrics/prometheus_files.go`: `ownProviderNamespace` is set at lines 123-129; the provider-prefix deletion guard is at lines 142-153; `providerSourcePresent` matches only current non-application sources at lines 180-193. This correctly protects provider-prefixed files during application-only syncs and preserves a non-matching foreign provider file during a provider sync.

However, a provider-prefixed file for a source that is no longer selected is also non-matching. The code therefore leaves it in place. If the current provider source set is empty, `ownProviderNamespace` is false and every provider file is left. If another provider source remains, the old file still fails `providerSourcePresent` and is left. The `baseharbor-providers` scrape job continues globbing `provider--*.json` (`internal/metrics/prometheus_render.go:222-226`), so a stale non-secure target remains eligible for scraping after deselection. For secure targets, the dynamically rendered exact-file job disappears with the source, but the orphan file is still retained.

The source comments at `prometheus_files.go:110-116` and `:143-147` document the preservation policy for files the current sync cannot prove it owns. They do not resolve ownership of a file previously written by this same sync; without retained ownership evidence it is treated as foreign. This makes preservation of foreign state work, but leaves a stale-target cleanup gap. A previously emitted file for a deselected source may not remain scrapeable as an accepted outcome unless the task/owner explicitly changes that lifecycle contract.

**Recipe:** In `prometheus_files.go:98-153`, reconcile against explicit prior ownership for this provider placement, not only the current source list. Persist or consume an authoritative set of provider filenames this writer previously created; remove previously owned names absent from the desired current set, while retaining files outside that set. Keep application-only syncs from touching the provider namespace. Extend `regvisibility_regression_test.go` with a sequence that seeds an owned provider target and a foreign provider target, then deselects the owned source (including the no-provider-sources case): assert the stale owned target is removed and the foreign file remains byte-identical. Also retain the existing app-only preservation and unrelated-provider preservation cases.

**Stop criterion:** do not accept while a deselected previously owned `provider--*.json` target remains in the active provider glob, or while the fix can delete/rewrite a foreign provider file.

## B1 — test must exercise the actual emitted routing table — REQUEST CHANGES

The new test does call `prometheusConfig(nil, false, nil)` at `regvisibility_regression_test.go:337`, but it does not test which emitted glob selects each filename. `globSelects` at lines 362-388 only checks that the job name occurs, then scans file paths across the whole config; it never restricts the scan to the named job. More decisively, `globMatch` at lines 397-404 ignores its `glob` argument entirely and hardcodes filename-prefix/split rules based on `jobName`. Thus changing the actual provider glob to an incorrect pattern can still pass this test. It tests the helper's expected classification, not the rendered Prometheus routing table.

The production config currently emits the applications globs at `prometheus_render.go:194-200`, the provider glob at `:222-226`, and secure provider exact-file globs at `:233-249`. The disjoint filename design is correct by inspection: application files use `application--...`; non-secure provider files use `provider--<hash>.json`. The required regression proof is still missing because the test does not execute those strings as globs in their respective job sections.

**Recipe:** In `regvisibility_regression_test.go:337-404`, parse the rendered Prometheus YAML into scrape jobs and their `file_sd_configs.files`, then apply the parsed glob patterns to the generated application and provider filenames. Assert that the `provider` and `provider-secure` application targets are selected by the application job and never the provider job; assert the real `provider--<hash>.json` target is selected by the provider job and not the application job. Ensure the job-to-glob association is taken from the parsed YAML and the test fails if the rendered patterns are changed to a colliding or non-matching pattern.

**Stop criterion:** do not accept until the regression fails when the emitted job glob is deliberately made wrong, and passes only for the correct rendered routing table.
